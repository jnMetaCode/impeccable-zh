> **还需要补充的上下文**：质量标准和发布约束。

Polish 是精修，绝不能暗中变成重新设计。保留现有的视觉世界、内容、行为以及范围外的一切。如果概念本身有问题，应明确指出，并建议重新设计或使用 `bolder`，不要偷偷替换方案。

检测器的结果只能证明存在缺陷，不能证明质量达标。必须检查实际渲染体验和真实交互路径。

## 1. 建立系统认知

阅读 DESIGN.md，并查看有代表性的 token、共享组件、模式和相邻流程。如果没有正式设计系统，就遵循项目中连贯一致的惯例。

修复前先对每一处偏差分类：

- **缺少 token：** 系统需要一个可复用的值；
- **一次性实现：** 应改用现有共享组件或模式；
- **概念不匹配：** 流程、信息架构或层级与产品中的相似区域不同；
- **局部缺陷：** 实现本身不完整或不一致。

在最小且正确的层级修复根因。如果无法推断具有约束力的系统原则，应先询问。

## 2. 收集证据

亲自以界面的代表性尺寸使用该功能：Web 端检查桌面与移动端；原生平台（`ios` / `android` / `adaptive`）则按照相应平台参考文档中“验证构建”的说明，在模拟器、仿真器或真机上覆盖已发布的设备类别并截图。确认：

- 路径在功能上是否完整；
- 预期质量标准和可用时间；
- 已知限制或刻意暂未完成的工作；
- 用户实际会遇到的状态、内容长度、角色和输入方式。

如果已有评审记录，将它作为一项输入：

```bash
{{scripts_path}}/impeccable critique-storage latest "<resolved target>" --json
```

退出码 0 会返回 JSON，其中包含最新快照的 `body` 和精确的 `snapshot_file` 标识。保留 `snapshot_file`，直到本轮结束。对于本地文件目标，辅助工具会把文件当前内容的精确指纹与评审时记录的指纹比较。未变化的已暂存、未暂存或未跟踪内容仍视为当前版本；任何字节变化、文件删除或被非文件对象替代，都会关闭它所识别的待办，同时保留趋势历史，并以退出码 2 结束。URL 目标没有本地指纹，在显式关闭前始终视为当前版本。当快照仍为当前版本时，纳入 `body` 中相关的 P0/P1 问题，并说明读取了哪个快照。退出码 2 表示不存在快照或目标已变化。无论哪种情况，都要独立完成一轮检查。

## 3. 分诊

将功能缺陷与外观问题分开，并按以下顺序修复：

1. 中断或阻塞任务、造成数据丢失、状态误导和无障碍路径失效的问题；
2. 缺少加载、空、错误、成功、禁用和权限状态；
3. 流程、层级、响应式行为和设计系统偏差；
4. 视觉与动效不一致；
5. 代码和资源清理。

不要在其他区域仍低于同一质量标准时，只把一个角落打磨到完美。

## 4. 精修完整路径

### 流程与层级

- 与相邻功能的心智模型、术语、渐进披露、路由、保存行为，以及乐观或悲观更新模式保持一致。
- 让主要任务和当前状态一目了然，同时避免把所有元素压成同一权重。
- 确保进入、过渡、空状态和恢复路径彼此连通，而不是像孤立页面一样各自运行。

### 布局与文字

- 对齐项目的网格和间距尺度；既修正数学对齐，也修正视觉对齐。
- 紧密组合相关内容，并用充足间距分隔不同组。
- 相同角色的排版应保持一致；测试行长、换行、本地化扩张、缩放和字体加载。
- 验证每个受支持的视口，而不是只修正当前截图。

### 色彩、图像与图标

- 使用语义 token，并让颜色含义在不同主题中保持稳定。
- 验证每种状态下文字、控件和焦点的对比度。
- 保持图标家族、描边或字重、尺寸和视觉对齐一致。
- 防止图片引起布局偏移；使用正确的宽高比、响应式图片源和有用的 alt 文字。

### 交互与状态

- 每个控件都需要恰当的 default、hover、focus、active、disabled、loading、error 和 success 行为。
- 保留可见的键盘焦点、合理的 Tab 顺序、标签，以及符合平台规范的触控目标。
- 动效应连贯、可中断且性能良好。不要仅为了让精修显得可见而添加动画。
- 验证产品可能遇到的超长、缺失、本地化、离线、慢速和权限受限内容。

### 内容与代码

- 保持术语、大小写、标点和事实性文案一致。修改事实陈述前先询问。
- 删除调试输出、死代码、未使用的 import、过时样式和精修过程中产生的重复实现。
- 如果某种模式归设计系统所有，用共享组件替换自定义实现。
- 将真正可复用的值提升为 token；不要为一个局部例外创建系统抽象。

## 5. 验证并收尾

再次走完完整路径，并在适用时使用鼠标、键盘和触控。检查：

- Web 端的移动、中间和宽屏布局；原生端在两个受支持方向上的手机和平板尺寸类别；
- 加载、空、错误、成功、禁用、长内容和缺失内容状态；
- 缩放、对比度、焦点、语义和屏幕阅读器名称；
- 所有位置的控制台错误、布局偏移、交互延迟和图片加载；Web 端的受支持浏览器；原生端的受支持系统版本、运行时警告和掉帧；
- 与 DESIGN.md、相邻功能及用户范围保持一致。

遵循 `impeccable context` 和 hooks 提供的质量指导，然后运行其他相关 QA 命令。只有在没有自动检测器运行时，context 才会要求手动扫描；绝不要再增加一轮检测器扫描。修复真实缺陷，只记录范围明确且有意保留的例外。检测结果干净不能替代视觉判断。

最后检查源码 diff：删除意外改动、孤立代码、冗余值和临时产物。只有当功能在完整路径上已经完备且精修一致时，才能发布。

当本轮处理的某个快照中的全部 Priority Issue 都已解决时，关闭该快照：

```bash
{{scripts_path}}/impeccable critique-storage close "<resolved target>" "<snapshot_file returned by latest>"
```

这只会关闭本轮实际处理的快照；如果期间产生了更新的评审，其待办仍然有效。在没有读取快照、没有保留 `snapshot_file` 或仍有 Priority Issue 时，不要关闭快照。
