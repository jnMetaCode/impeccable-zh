布局把产品优先级转化为阅读顺序、分组、节奏和可用空间。移动元素前，先诊断结构问题。

---

## 访客模式

- **Persuade + Experience：** 当所选视觉世界有充分理由时，构图可以不对称、流动或有意打破常规。
- **Operate + Read：** 可预测的结构、稳定的密度和易于导航的线性顺序本身就是可供性。
- **原生平台：** 按照 [ios.md](ios.md) 或 [android.md](android.md) 处理导航、安全边距、适配和触控目标。

保留既有视觉世界。layout 命令只改变其中的结构；替换视觉身份属于 [new-work.md](new-work.md)。

## 两项独立评估

如果子 Agent 工具可用且获准使用，应独立执行以下两项评估；否则按顺序自行完成。

1. **布局评估：** 检查有代表性的状态和视口，并用渲染结果或源码证据回答每个问题：
   - **阅读顺序：** 使用眯眼测试。模糊细节后，是否仍能依次识别主要元素、次要元素和主要分组？
   - **分组：** 相关项目是否彼此接近、不同分组是否充分分离，还是依靠容器弥补薄弱的邻近关系？
   - **节奏：** 紧凑与宽松的间隔是否形成有意节奏，还是重复一种间距直到所有内容权重相同？
   - **结构：** 拓扑是否符合内容和任务？重复卡片、分栏或区块真的等价，还是仅仅来自框架默认值？
   - **密度：** 每个区域的信息量是否符合使用频率、决策复杂度和访客模式？
   - **适配：** 在窄屏、中间宽度、宽屏、缩放和本地化状态下，哪些内容会重排、折叠、换行、滚动或固定？DOM 与焦点顺序是否仍和视觉顺序一致？
   - **极端情况：** 长内容、空状态、浮层、粘性元素、安全区域和较小触控目标是否暴露结构缺陷？
2. **机械扫描：** 运行：

```bash
{{scripts_path}}/impeccable detect --json --scope layout [target files or dirs]
```

同时检查检测器无法判断的任意间距、溢出、层叠和容器行为。第一项评估中不要混入机械扫描证据，编辑前再综合两轮结果。干净的扫描结果不能证明层级或节奏正确。

## 确立空间主张

编辑前明确：

- 主要阅读或任务路径；
- 哪些内容属于一组，哪些必须分开；
- 哪个元素主导，哪个提供支持；
- 预期密度和间距节奏；
- 结构如何随容器、视口、输入方式和内容极值变化。

选择能够表达这些关系的最简单结构模型。根据布局原语所控制的关系使用它们，并用语义化名称定义可复用的间距和容器角色。

## 应用

- 按含义分组。添加容器或装饰前先使用邻近关系。
- 通过紧凑与宽松间隔之间有意的对比创造节奏。
- 使用有文档的间距尺度，不使用一次性数值。以 4 为基础通常能提供仅使用 8 倍数时缺少的实用中间档。
- 让层级服从产品优先级，而不是框架默认值。
- 让不同内容在视觉上保持区别，但不要把每个分组都变成孤立组件。
- 让响应式行为改变结构：根据仍然重要的内容重排、折叠、重流或揭示。
- 同一组件出现在不同情境时，优先使用能感知容器的组件。
- 当 `gap` 比子元素 margin 更直接地表达同级关系时，使用 `gap`。
- 即使可见标记很小，也要保持触控目标可用。
- 只有在能澄清状态或层级时才使用纵深。
- 检查实际渲染结果后再做视觉校正。

变化本身不是目标。重复应帮助识别；只有内容或优先级变化时才打破重复。

## 验证

- 眯眼测试仍能依次显示主要元素、次要元素和主要分组。
- 阅读和任务路径在每个受支持尺寸下都保持清晰。
- 相关内容自然成组，无关内容不会混在一起。
- 紧凑与宽松间距形成有意节奏，而不是单调重复。
- 密度符合使用频率和内容复杂度。
- 长文本、空状态、本地化、缩放和动态内容不会破坏结构。
- 键盘、触控和辅助技术顺序与视觉顺序一致。
- 最终机械扫描不存在无法解释的问题。

逐项用渲染或源码证据回答，然后重新运行扫描。不要用一句“是”代替验证。

结构稳定后，交给 `{{command_prefix}}impeccable polish`。

## Live 模式签名参数

每个变体都声明一个粗粒度 `density` 参数，并基于 `var(--p-density, 1)` 编写间距。

```json
{"id":"density","kind":"range","min":0.6,"max":1.4,"step":0.05,"default":1,"label":"Density"}
```

只有拓扑确实出现分支时，才能再添加一个结构参数。遵循 [live.md](live.md) 的参数契约。
