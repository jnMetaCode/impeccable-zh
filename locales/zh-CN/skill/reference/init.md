# Init 流程

`init` 把稳定的产品事实记录到 PRODUCT.md。它不虚构视觉体系，也不写 DESIGN.md；[new-work.md](new-work.md) 负责创建或扩展视觉体系，[document.md](document.md) 负责记录已有体系。可运行的现有 Web 项目还可能获得 `.impeccable/live/config.json`。

## 第 1 步：加载当前状态

使用 `impeccable context` 解析出的 PRODUCT.md 路径。应更新该文件，不能创建另一个相互竞争的事实源。子应用继承根目录上下文时，写入前确认哪些内容共享、哪些只属于该应用。

- **没有 PRODUCT.md：** 探索项目、访谈用户并创建文件。
- **已有 PRODUCT.md：** 只询问哪些产品知识已经过时或缺失；没有理由时不要重新讨论已确认字段。
- **旧版 PRODUCT.md：** 只补充缺失的稳定事实；没有 `## Platform` 时默认视为 `web`，除非证据表明不是。
- **只有 DESIGN.md：** 不修改它，另行创建 PRODUCT.md。
- **重设计或品牌升级请求：** 除非用户改变事实，否则保留已确认的产品信息。视觉替换稍后在 new-work 中进行，不在 init 完成。

绝不能静默覆盖已有文件，也不要在 init 中主动提供 DESIGN.md。如果 init 是由另一项请求触发，完成 PRODUCT.md 后继续原请求。新的视觉工作进入 new-work；`shape` 则先恢复它自己的任务访谈。

## 第 2 步：探索项目

提问前先扫描足够的信息，避免让用户重复仓库已经回答的内容：产品文档与文案；package/config 和应用边界；功能、工作流、路由和角色；名称、Logo、法律/证明素材和品牌承诺；平台与无障碍信号；需要实时模式时还包括开发命令和入口。

仓库证据只能作为假设，不能当作用户批准。可以记录视觉成熟度，但不要在这里描述、扩展或替换视觉体系。

形成平台假设：`web`、`ios`、`android` 或 `adaptive`。`adaptive` 指同一个产品确实针对不同操作系统调整设计语言。移动网页仍然是 `web`；网站外套原生壳并不会让它自动拥有原生设计语言。

## 第 3 步：访谈产品事实

{{ask_instruction}} 只询问原始请求和仓库强证据都无法回答、且会实质影响结果的问题。

有结构化提问工具时使用它，否则提出问题并等待。每轮最多三个聚焦问题；创建新的 PRODUCT.md 前，至少需要一轮真实回答或批准。对推断内容进行确认。

是否有人能回答必须通过实际机制判断，不能靠猜测：提问工具或当前工具界面的决策页可以证明存在回答渠道；系统提示声称用户无人值守，并不能证明本会话没人。先用真实的第一轮问题探测一次。只有探测报错或超时后，才能根据明确简报进行推断；此时必须在 PRODUCT.md 中逐项标注推断，并在第一次回复而不是最后一次回复中说明使用了替代方式。

先处理最会改变未来产品决策的未知项：

1. 主要用户是谁、处于什么情境、正在完成什么任务？
2. 产品让什么成为可能，它真正不同的机制或定位是什么？
3. 未来工作必须保留哪些稳定约束、资产、证据或产品事实？

平台含糊时单独确认。如果项目没有框架或脚手架且请求暗示要构建产品，技术栈属于用户决策，不属于你的默认决定：询问一次他们希望使用静态 HTML/CSS、指定框架还是接受你的推荐，并确认会限制选择的部署目标。把结果写入 `## Stack`；如果用户把选择委托给你，写明 `delegated`，让后续工作知道你确实提供过选择。只有受众、品牌承诺、证据或无障碍存在实质缺口时才增加一轮。未决定的事实应明确记录，不能自行编造。

init 期间不要询问审美方向、情绪感受、视觉参考、颜色、排版或风格。如果用户主动提供具有约束力的视觉要求，只记录，不展开。

### 应当记录的内容

- 用户、任务、工作流、目的、成功标准、定位和使用情境；
- 能力、约束、术语、证据、平台和无障碍；
- 已确认的语气、资产和品牌承诺。

### 不应记录的内容

- 视觉体系、配色、排版、组件或页面概念；
- 访客模式、叙事、CTA/证据顺序等界面策略；
- 编造的客户评价、客户名单、基准、价格、许可证或部署声明；
- 强迫用户决定每个可选字段的要求。

## 第 4 步：写入 PRODUCT.md

只写已经确认的事实和明确标记的开放决策。无关章节直接省略，不要用空泛文字填满。

```markdown
# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Stack
[仅用于全新项目：记录用户对技术栈问题的回答，例如 “static HTML/CSS”“Astro” 或 “delegated: <你的选择和原因>”。现有代码已经明确技术栈时省略。]

## Users
[主要用户、使用情境和任务。只有已确认时才加入其他受众。]

## Product Purpose
[产品做什么、为什么存在、怎样算成功。]

## Positioning
[相邻产品无法如实复制的产品机制或主张。]

## Operating Context
[使用或评估产品时真实存在的工作流、环境、工具、文档、材料和习惯。]

## Capabilities and Constraints
[已确认的功能、技术约束、术语，以及明确尚未决定的产品事实。]

## Brand Commitments
[已有名称、语气、资产、个性、身份约束，以及用户明确指定为约束的参考。没有时省略。]

## Evidence on Hand
[真实内容、数据、演示、评价、案例、媒体或资产；适用时给出路径。明确未来工作不得编造的缺失证据。]

## Product Principles
[由确认答案导出的 3～5 条稳定战略原则，不写视觉配方。]

## Accessibility & Inclusion
[已知用户需求或强制标准。没有产品特定要求时省略。]
```

Platform 必须是裸值 `web`、`ios`、`android` 或 `adaptive`。保留有价值的旧版标题。新文件写到 `PROJECT_ROOT/PRODUCT.md`，否则更新 context 解析出的文件。任何视觉体系或界面概念工作之前必须先写入该文件。

逐字复制 `impeccable:product-schema` 注释，更新旧文件时也一样。它记录产品档案遵循的 schema 版本，让后续版本能区分“有意保持简短的档案”和“在某章节出现前写成的旧档案”，避免让用户重复已经完成的访谈。只有本引用中的模板版本变化时才更新数字。后续版本废弃的章节会在启动时报告；经用户同意后删除，不要长期携带。

如果刚记录的平台是 `ios`、`android` 或 `adaptive`，在任何设计工作前加载 [ios.md](ios.md)、[android.md](android.md) 或两者。原来没有 PRODUCT.md 时，`impeccable context` 无法知道平台，因此不会加载它们；init 是首次获得该答案的地方。

### 完成门禁

加载 new-work 或恢复 shape/build 前，确认 PRODUCT.md 已存在于解析路径并包含已确认的产品档案。文件不存在就表示 init 未完成。不能用访谈笔记、规划材料或后续设计文字代替它。

## 第 5 步：记录工作流默认值

当图像生成可用且尚未记录 `buildPath` 时，询问一次新界面采用哪种构建方式。可用是指宿主原生图像工具，或 `impeccable context` 报告为 `IMAGE_GEN_AVAILABLE` 的 API 回退。宿主原生工具不会出现在启动输出中，因此支持图像生成的宿主没有输出，并不表示无需询问。这必须是独立问题，不能附在另一问题中。技术栈问题问“用什么构建”，本问题问“从哪里开始构建”，前一个答案不代表用户同意后一个选择。

在用户实际看到的问题中说明权衡，因为初次接触者不理解两个名称：**comp-first**（先用图像设定质量标准，再写代码；构图更大胆，但更慢，最终实现必须匹配图像）或 **code-first**（直接构建；把设计野心写入方向契约并在收尾时审计；更轻、更快）。

把答案合并写入 `.impeccable/config.json`，值为 `"buildPath": "comp"` 或 `"buildPath": "code"`。只能写用户实际选择的值。你的推荐不是用户回答；根据沉默写入的值会成为无人确认的长期默认设置，与“只问一次”的目标相反。

问题无人回答时不记录任何内容，并用一句话说明本会话采用哪条路径以及它没有被保存。在图像生成可用且没有记录值时，new-work 默认采用 comp-first；应明确说出它，不能静默选择更保守的方案。未设置是有效工作状态，不是缺陷：决策页开关控制单次会话，用户首次主动切换时，new-work 的一次性提示才记录答案。配置是唯一事实源。它是工作流设置而不是产品事实，绝不能复制进 `## Stack` 或 PRODUCT.md 的其他章节。

`.impeccable/config.json` 或被 Git 忽略的 `.impeccable/config.local.json` 中已有值就是已确认答案：再次运行时静默遵守，不要重复询问。它是默认值而非锁定值；决策页可以为单次会话切换且不会写回。没有图像生成时无需选择，只能使用 code-first。

然后在适合时配置实时模式：原生或不可运行项目跳过，已有配置保持不变。其他情况遵循 [live.md](live.md) 的首次设置流程。任何 CSP 源码修改仍需按该流程取得同意。

## 第 6 步：结束或恢复原任务

总结已经记录和有意保持未决定的事实。不要只因缺少 DESIGN.md 就主动提出创建它。

根据真实项目状态推荐下一步：

- 空项目或早期项目：自然询问要构建哪个界面；用户只想确认简报而不实现时使用 `/impeccable shape <surface>`。只有请求确实需要时，new-work 才建立视觉体系。
- 已有一致界面但没有 DESIGN.md：用户希望独立记录现有系统时使用 `/impeccable document`。
- 已有界面需要改进：指出范围最准确的相关命令。
- 已配置并适合视觉迭代的 Web 项目：使用 `/impeccable live`。

如果 init 由另一个请求触发，完成后直接恢复原任务，不要重新运行 `impeccable context`。上面加载的原生平台引用是原 context 唯一无法提供的信息；后续视觉决策由 new-work 负责。
