### 目的

解析出一个稳定目标，执行两项相互独立的评估，综合形成设计评审，持久化快照，并询问用户下一步要改进什么。聊天回复是主要交付物；快照只是本轮归档。

### 硬性不变量

- 评估 A（设计评审）和评估 B（检测器/浏览器证据）都必须执行。
- 只要环境提供 sub-agent/Task 工具，A、B 就必须由两个隔离的 sub-agent 执行。在当前上下文内串行执行虽然“可行”，但不被允许，属于降级运行。只有没有 sub-agent 工具时（或会请求授权的环境中用户拒绝时）才可内联。
- 任何原因导致降级时，报告第一行必须是：`⚠️ DEGRADED: single-context (<reason>)`。静默降级等于评审失败。
- A 必须在检测器发现进入父级综合上下文之前完成。检测器输出虽是确定性的，仍会锚定判断。
- 除非 `impeccable detect` 缺失或真实尝试后崩溃，否则跳过检测器即为失败。
- 目标可查看且浏览器检查可用时，必须检查浏览器。
- 只为评审可视化启动的本地服务必须后台运行，记录停止方法，并在最终报告前停止，除非用户要求保持运行。
- 只有脚本注入成功且检测器确实在页面运行，才能声称存在用户可见 overlay。
- 问题必须是回复的最后内容。先写完报告再提问，之后不得追加内容；结构化提问后的文本会被扣留到用户回答，导致报告看起来未执行。
- 一轮运行若既没有针对性问题，也没有字面行 `Questions skipped: <reason>`，就是未完成。报告不是终点，闭环才是。

### 设置

1. **解析目标**为具体文件路径或 URL。二者指向同一界面时优先源码路径：端口会漂移，路径不会。
   - “首页” → `site/pages/index.astro` 或 `index.html`
   - “设置弹窗” → 主要组件文件
   - “此页面” → 当前 URL 或源码文件
2. **确认目标可生成规范 slug**：
   ```bash
   {{scripts_path}}/impeccable critique-storage slug "<resolved-path-or-url>"
   ```
   后续命令也接受解析后的目标并内部生成同一 slug；不要手写 slug。若命令非零退出，本轮跳过持久化和趋势，但继续评审。
3. 若 `.impeccable/critique/ignore.md` 存在则读取。静默删除匹配的发现；这是 critique 唯一会消费的历史运行输入。

### 评估编排

把 A、B 委派给不同 sub-agent，双方不得看到彼此输出。综合前不得向用户展示发现。

所有执行环境的 sub-agent 门禁：
- 除非下方环境专用门禁覆盖，否则只要暴露 sub-agent/Task 工具，就并行生成两个隔离 agent；这是强制默认行为，不能为了快而内联。
- “不可用”只表示会话没有暴露 sub-agent/Task 工具（或会询问的环境中用户拒绝），不表示使用不方便。
- 仅在 sub-agent 不可用时依次执行：完成并记录 A，再执行 B，最后综合并输出降级横幅。
- 无论采用哪条路径，都要在报告头声明。跳过 sub-agent 又不显示横幅是最常见的失败。

<codex>
Codex sub-agent 门禁（覆盖上述默认门禁；Codex 权限模型要求生成前征询）：
- 询问是正常路径，不算降级。用户同意并生成 agent 后属于双 agent 路径，不能仅因询问而显示降级横幅。
- 若暴露 `spawn_agent`，且用户明确允许 sub-agent、委派或并行工作，立即生成 A、B。
- 若暴露 `spawn_agent` 但用户未明确允许，只问一次：“Impeccable critique is designed to run two independent sub-agents for an unanchored assessment. May I use sub-agents for this critique?”然后停止等待。
- 用户同意则生成；拒绝则串行执行，报告以 `⚠️ DEGRADED: single-context (sub-agents declined by user)` 开头。
- 未暴露 `spawn_agent` 时不要询问，串行执行并使用 `⚠️ DEGRADED: single-context (spawn_agent unavailable in this session)`。
- 获准后生成失败，则串行执行并使用 `⚠️ DEGRADED: single-context (sub-agent spawn failed: <exact error>)`。
优先使用 `fork_context: false`，以自包含 prompt 提供 cwd、目标、Live URL、参考资料、产品上下文和输出契约。若使用 `fork_context: true`，省略 `agent_type`、`model`、`reasoning_effort`。
</codex>

浏览器自动化可用时，每项评估各自创建新标签页。即使已有标签页正位于目标 URL，也不得复用。

### 评估 A：设计评审

读取相关源码；浏览器自动化可用时目视检查页面。以设计总监视角思考。

评估：
- **设计特异性**：构图、交互和视觉语言是否扎根于本产品，还是换成无关产品也成立？必须在看到检测器输出前判断。
- **整体设计**：层级、信息架构、情感契合、可发现性、构图、排版、颜色、无障碍、状态、文案和边界情况。
- **认知负荷**：参考下文[认知负荷评估](#cognitive-load-assessment)，报告清单失败项和可见选项超过 4 个的决策点。
- **情感旅程**：峰终定律、情绪低谷、高风险时刻的安抚。
- **Nielsen 启发式**：参考下文[启发式评分指南](#heuristics-scoring-guide)，对 10 项各打 0–4 分；模式适用性规则允许不适用的项标记 `n/a`，不能强行评分。

返回：设计特异性结论、启发式得分、认知负荷、情感旅程、2–3 个优点、3–5 个优先问题、Persona 风险、次要观察和启发性问题。

### 评估 B：检测器 + 浏览器证据

运行内置检测器并收集浏览器可视化证据。B 是必需项，在 A、B 都结束前必须与 A 隔离。

CLI 扫描：
```bash
{{scripts_path}}/impeccable detect --json [target]
```

- 标记文件/目录作为 `[target]` 传入；不要传纯 CSS 文件。
- URL 跳过 CLI 扫描，使用浏览器可视化。
- 超大目录（500+ 个可扫描文件）应缩小范围或询问用户。
- 退出码 0 表示无发现，2 表示有发现。
- 检测器入口缺失或加载失败时，报告“确定性扫描不可用”，继续浏览器/人工评审。

当目标可查看且浏览器自动化可用时，必须做浏览器可视化。本地文件使用 localhost 开发/静态 URL；除非浏览器明确支持此流程，否则避免 `file://`。Overlay 流程：

1. 新建标签页并导航。优先使用环境原生/browser-canvas 截图路径；只有没有原生浏览器工具时才自写 Playwright/Puppeteer 脚本。
2. 通过设置 `document.title` 并追加 `<script>` 标签，预检可变注入能力。只读 evaluate API 不算。
3. 无法修改时，跳过 Live 服务、浏览器展示和注入，报告回退信号。
4. 可以修改时，启动 `{{scripts_path}}/impeccable live-server --background`，环境支持则展示浏览器，标记 `[Human]`，滚到顶部，注入 `http://localhost:PORT/detect.js`，等待 2–3 秒，读取 `impeccable` console 消息，然后停止 Live 服务。
5. 多视图目标应选 3–5 个代表页面注入。

<codex>
Codex Browser 注意：使用 Browser skill。不要浪费一次 Browser 尝试打开 `file://`。只有确认可变脚本注入成功后，才为 `[Human]` overlay 路径调用 `visibility.set(true)`，并用 `get()` 验证。使用 `tab.dev.logs({ filter: "impeccable" })` 获取 console 结果。其 Playwright `evaluate(...)` 表面只读，不得依靠它修改页面。
</codex>

返回：CLI 发现的 JSON/计数、适用时的浏览器 console 发现、误报，以及被跳过/失败的浏览器步骤与具体原因。

B 返回可用 CLI 发现后直接复用。除非 B 失败、输出截断，或缺少计数、规则名、文件位置，否则父上下文不得重跑 `impeccable detect`。

<codex>
Codex 失败核算：最终 Run Notes 必须包含目标 slug、忽略清单、评估独立性、CLI 检测器、浏览器可见性、overlay 注入、Live 服务清理、临时文件清理，以及所用回退信号。报告组装完成后，不要再执行仓库状态检查、迟到的 API 探索或无关验证。
</codex>

### 生成综合评审报告

把两项评估综合为一份报告，不得简单拼接。说明 LLM 评审与检测器在哪里一致，检测器发现了哪些 LLM 遗漏的问题，以及哪些检测结果是误报。

聊天回复是面向用户的主要交付物。必须在聊天中完整展示下列结构化评审，不能用摘要和链接代替；持久化快照只是归档。

<codex>
Codex 最终回复注意：`$impeccable critique` 会产出报告，因此最终聊天回复应有意超过通常的简短收尾风格。除非用户明确只要摘要，否则不要把标题写成“Critique Summary”。
</codex>

像设计总监一样组织反馈：

#### 报告头来源

第一行必须声明评估运行方式，确保降级永不静默：
- 双 agent：`Method: dual-agent (A: <agent-id> · B: <agent-id>)`
- 降级：`⚠️ DEGRADED: single-context (<reason, e.g. no sub-agent tool exposed>)`

#### 设计健康分
> *参考下文[启发式评分指南](#heuristics-scoring-guide)。*

以表格展示 Nielsen 10 项启发式得分：

| # | Heuristic | Score | Key Issue |
|---|-----------|-------|-----------|
| 1 | Visibility of System Status | ? | [specific finding or "n/a" if solid] |
| 2 | Match System / Real World | ? | |
| 3 | User Control and Freedom | ? | |
| 4 | Consistency and Standards | ? | |
| 5 | Error Prevention | ? | |
| 6 | Recognition Rather Than Recall | ? | |
| 7 | Flexibility and Efficiency | ? | |
| 8 | Aesthetic and Minimalist Design | ? | |
| 9 | Error Recovery | ? | |
| 10 | Help and Documentation | ? | |
| **Total** | | **??/[applicable max]** | **[Rating band]** |

适用最高分等于实际评分项数量乘 4：十项全适用为 **/40**，两项 `n/a` 时为 **/32**。部分评分绝不能仍写 `/40`。

诚实评分。4 分意味着真正优秀；多数真实界面得分在 20–32/40。

**模式适用性**：Persuade 和 Experience 界面（落地页、活动页、作品集、作品正文）可把第 7 项（灵活性与效率）和第 10 项（帮助与文档）标为 `n/a`；其他确实不适用于当前界面的项也可如此。Score 单元格写 `n/a` 并附一行原因，按适用最高分重新归一化总分，如两项不适用时写 **24/32**，使评级区间保持同比例。快照必须记录适用最高分和 `n/a` 项。

#### 设计特异性结论

**从这里开始。** 结果是否像为此产品专门创作，还是类别内可以互换？

**LLM assessment**：不受锚定影响的特异性判断，覆盖整体一致性、结构雷同、类别可互换选择及错失的产品性格机会。

**Deterministic scan**：概括自动检测结果、计数和文件位置，注明检测器补获的遗漏和误报。

**Visual overlays**（注入成功时）：告知用户 overlay 已在浏览器的 **[Human]** 标签页可见并高亮问题，概括 console 输出。若尝试过但注入失败，明确说明没有可靠的用户可见 overlay，并报告回退信号。

#### 整体印象
简短直觉反应：有效之处、无效之处和唯一最大的机会。

#### 做得好的地方
列出 2–3 项，具体说明为何有效。

#### 优先问题
按重要性排列 3–5 个最有影响的问题。

每个问题标注 **P0–P3 严重度**（定义见[问题严重度](#issue-severity-p0p3)）：
- **[P?] What**：清晰命名问题
- **Why it matters**：如何伤害用户或破坏目标
- **Fix**：具体如何修改
- **Suggested command**：可处理它的命令（只能来自 {{available_commands}}）

#### Persona 风险
> *参考下文[Persona 测试](#persona-based-design-testing)。*

根据界面类型自动选择最相关的 2–3 个 Persona。若 `{{config_file}}` 包含由 `impeccable init` 生成的 `## Design Context`，再从受众/品牌信息生成 1–2 个项目专用 Persona。

让每个 Persona 走完主要操作并列出具体风险。不要写泛泛的 Persona 描述，而要指出具体失败元素和交互。例如 Alex 缺少快捷键、主要操作需点击八次、被迫经过 onboarding；Jordan 遇到纯图标导航、技术化错误文案且没有帮助。

#### 次要观察
简记值得处理但影响较小的问题。

#### 值得思考的问题
提出可能打开更好方案的挑战性问题，例如主要操作能否更突出、是否必须如此复杂、更自信的版本会是什么样。

<codex>
#### Run Notes
保持精简。记录目标 slug、忽略清单、评估独立性、CLI 检测器、浏览器可见性、overlay 注入、Live 服务和临时文件清理状态。失败或跳过的步骤需给出具体观察原因和回退信号。持久化完成后，最终聊天回复还要记录快照写入与趋势读取状态。

Run Notes 只出现在最终聊天中，不写入快照正文，因为持久化、趋势读取和临时清理发生在快照写入后；否则归档会留下“等待持久化”之类的过时状态。
</codex>

**记住**：直接、具体、同时说明问题及其用户影响，并给出明确建议。彻底删掉“可以考虑探索”。严格排序；若一切都重要，就没有重点。不要淡化批评，开发者需要诚实反馈才能交付优秀设计。

### 交付报告

现在先把完整报告写入聊天回复，再做任何持久化。报告是交付物，后续只是记账。

必须先做这一步，因为最常见的失败是只把报告写进持久化 heredoc，然后以一份用户从未读到的完美归档结束。只存在于 `.impeccable/critique/` 的报告等于没有交付。持久化也不是本轮终点；之后仍要追加趋势和闭环问题。

### 持久化快照

报告定稿后写入 `.impeccable/critique/`，方便用户回看，也使 `{{command_prefix}}impeccable polish` 无需复制粘贴就能读取优先问题。若设置阶段 slug 为 null（目标模糊或只是根目录），跳过本节。

1. 把正文写入临时文件再交给 helper。包含已经向用户交付过的完整评审（启发式表格、特异性结论、优先问题、Persona 风险、次要观察和问题），但在后续“询问用户”/“建议操作”之前停止。它只是副本，不是首次交付。<codex>临时正文不包含 Run Notes。</codex>
2. 通过 `IMPECCABLE_CRITIQUE_META` 传入结构化元数据并写入：
   ```bash
   IMPECCABLE_CRITIQUE_META='{"target":"<user phrasing>","total_score":<n>,"max_score":<n>,"na_heuristics":"<comma-separated numbers, or empty>","p0_count":<n>,"p1_count":<n>}' \
     {{scripts_path}}/impeccable critique-storage write "<resolved target>" <body-file>
   ```
   `max_score` 是表格的适用最高分；本地文件还会记录精确内容指纹。Helper 会输出写入的绝对路径。保留快照文件，由 polish 关闭，本轮不关闭。
3. 写入尝试结束后，无论成功与否都删除临时文件。失败时在最终输出简记 `temp-file cleanup failed: <reason>`，但不阻断评审。
4. 读取最近五次趋势：
   ```bash
   {{scripts_path}}/impeccable critique-storage trend "<resolved target>" 5
   ```
5. 在报告后、问题前向用户输出一行趋势及写入路径。同一最高分可只标一次；最高分不同则逐项写分母并说明启发式集合不同，不可直接比较。旧条目缺少 `max_score` 时按 40。首次运行明确说没有趋势。
6. 进入下节发出问题；若数量允许跳过，则输出 `Questions skipped: <reason>`。未完成此闭环不算运行结束，也会让 `{{command_prefix}}impeccable polish` 无法继承优先问题。

这是 fire-and-forget。不要展示 helper JSON，只显示人类可读的趋势和路径。失败不应阻断后续流程；打印错误后继续。

### 询问用户

**展示发现之后**，根据实际发现提出针对性问题。{{ask_instruction}} 回答将塑造行动计划。问题必须与报告在同一消息中，先完整报告，最后提问；不得拆成两轮。

问题可覆盖：基于具体发现选择最优先类别；确认发现的语气不匹配是否有意；在“前三项 / 全部 / 仅关键问题”等具体范围中选择；确有必要时询问哪些区域不可改。

规则：每个问题必须引用报告的具体发现，不能泛问受众；最多 2–4 个；提供具体选项而非开放问题。只有优先问题少于 3 个时才允许跳过。最终回复必须包含针对性问题，或包含字面行 `Questions skipped: <reason>` 并写明允许跳过的数量。每题有 2–3 个与发现相关的具体选项，不得只用开放式问题结尾，也不得两者都没有。

### 建议操作

用户回答后，根据其选择形成具体行动计划。把优先问题映射到可用命令，但不要执行；用户决定何时开始。

#### 操作摘要

按执行顺序列出建议，每项都联系本轮发现：

1. **`{{command_prefix}}command-name`**：简述要修复的内容，并引用评审中的具体上下文
2. **`{{command_prefix}}command-name`**：简述具体问题与预期改进

规则：
- 只能推荐这些命令：{{available_commands}}
- 不要推荐与发现无关的命令，也不要把多个重叠命令堆在一起。
- 对每个命令说明它将处理哪些优先问题。
- 如果建议任何修复，以 `{{command_prefix}}impeccable polish` 作为最终步骤。
- 不要在未经用户确认时自动执行建议。

最后提示：

> 修复后重新运行 `{{command_prefix}}impeccable critique`，查看评分是否提升。

若用户选择开始修复，先执行最高优先级命令，并把本报告快照作为输入。若用户选择分阶段处理，明确第一阶段边界。若用户拒绝修改，保留快照，不再施压。长期设计上下文仍是约束，不能因一次评审而改写。

### 认知负荷评估

认知负荷是使用界面所需的全部脑力。过载会导致错误、挫败和离开。本参考用于识别并修复认知过载。

---

#### 三类认知负荷

##### 内在负荷：任务本身

用户目标固有的复杂度无法消除，但可以组织：把复杂任务拆成独立步骤；提供模板、默认值和示例等脚手架；渐进披露当前所需内容；把相关决策归组。

##### 外在负荷：糟糕设计

设计缺陷造成的脑力是纯浪费，必须坚决消除。常见来源包括：需要用户自行建立心智地图的混乱导航；迫使猜测含义的模糊标签；争夺注意力的视觉杂乱；妨碍学习的不一致模式；用户意图与结果之间的无谓步骤。

##### 相关负荷：学习投入

用于建立理解的脑力是有益负荷，会带来熟练度。用逐渐揭示复杂性的渐进披露、奖励学习的一致模式、确认理解正确的反馈，以及通过行动而非大段文字教学的 onboarding 来支持它。

---

#### 认知负荷清单

按以下八项评估界面：

- [ ] **单一焦点**：用户能否不受竞争元素干扰地完成主要任务？
- [ ] **分块**：信息是否以易消化的小组呈现（每组 ≤4 项）？
- [ ] **归组**：相关内容是否通过邻近、边框或共同背景在视觉上成组？
- [ ] **视觉层级**：屏幕上最重要的内容是否一眼可见？
- [ ] **一次一件事**：用户能否先专注一个决策，再进入下一项？
- [ ] **最少选择**：每个决策点的可见选项是否精简到 ≤4 个？
- [ ] **工作记忆**：用户是否必须记住上一屏信息才能操作当前屏？
- [ ] **渐进披露**：复杂度是否只在需要时出现？

计数失败项：0–1 项为低负荷（良好），2–3 项为中等（尽快处理），4 项以上为高负荷（需关键修复）。

---

#### 工作记忆规则

**人类工作记忆一次只能容纳 ≤4 项**（Cowan 2001 对 Miller 定律的修订）。在每个决策点，计算用户必须同时考虑的不同选项、操作或信息：≤4 可控；5–7 已接近边界，应归组或渐进披露；8+ 已过载，用户会跳过、误点或放弃。

实践：操作按钮采用 1 个主操作、1–2 个次操作，其余收入菜单；顶级导航 ≤5 项；长文保持一条阅读路径，把相关链接集中在末尾；文档侧栏每层可见同级项 ≤4 后再归组；作品集/画廊每屏只要求一个决策，不同时暴露筛选、排序和标签控制。

---

#### 常见认知负荷违规

1. **选项之墙**：一次展示 10+ 个无层级选择。按类别归组、突出推荐项、渐进披露。
2. **记忆桥**：完成第三步必须记住第一步内容。保持相关上下文可见，或在需要处重复。
3. **隐藏导航**：用户必须自行建立位置地图。始终显示当前位置，如面包屑、活动态和进度。
4. **术语屏障**：技术或领域术语迫使用户翻译。使用平实语言；不可避免的术语就地解释。
5. **视觉噪声底**：所有元素权重相同。建立一个主元素、2–3 个次元素，其余弱化。
6. **模式不一致**：相似操作在不同位置行为不同。相同操作类型必须使用相同 UI 模式。
7. **多任务要求**：同时要求阅读、决策、导航。顺序化步骤，一次做一件事。
8. **上下文切换**：为一个决策在屏幕、标签或弹窗间跳转。把所需信息并置，减少往返。

### 启发式评分指南

按 0–4 分评估 Nielsen 10 项可用性启发式。4 分表示真正优秀，而非“勉强够用”。

#### Nielsen 十项启发式

##### 1. 系统状态可见性

以及时、适当的反馈告知用户发生了什么。检查异步加载指示、保存/提交/删除确认、多步骤进度、导航当前位置和就地表单校验。

| 分数 | 标准 |
|---|---|
| 0 | 无反馈，用户只能猜测结果 |
| 1 | 极少反馈，大多数操作没有可见响应 |
| 2 | 部分状态有反馈，仍有重大缺口 |
| 3 | 大部分操作反馈清晰，只有小缺口 |
| 4 | 每个操作都有确认，进度始终可见 |

##### 2. 系统与现实世界匹配

使用用户语言和现实惯例，以自然逻辑顺序组织信息。检查熟悉术语、符合预期的信息顺序、可识别图标与隐喻、适合受众的领域语言和自然阅读流。

| 分数 | 标准 |
|---|---|
| 0 | 全是用户陌生的技术术语 |
| 1 | 多数内容混乱，需要领域专长才能导航 |
| 2 | 平实语言和泄漏术语混杂 |
| 3 | 基本自然，偶有术语需要上下文 |
| 4 | 始终流利地说用户的语言 |

##### 3. 用户控制与自由

用户需要从非预期状态快速逃离。检查撤销/重做、表单与弹窗取消、返回安全位置、清除筛选/搜索/选择，以及退出长流程的方式。

| 分数 | 标准 |
|---|---|
| 0 | 用户被困，只能刷新 |
| 1 | 出口隐蔽且难找 |
| 2 | 主流程有出口，边界情况没有 |
| 3 | 多数操作可退出和撤销 |
| 4 | 所有场景都有撤销、取消、返回与退出 |

##### 4. 一致性与标准

用户不应猜测不同文字、情境或操作是否含义相同。检查术语、操作结果、平台惯例、视觉系统和交互模式是否一致。

| 分数 | 标准 |
|---|---|
| 0 | 到处不一致，像多个产品拼接 |
| 1 | 大量相似事物外观或行为不同 |
| 2 | 主流程一致，细节分裂 |
| 3 | 基本一致，少量偏差不致混淆 |
| 4 | 系统完全统一且行为可预测 |

##### 5. 错误预防

优于优秀错误信息的是从源头防止错误。检查破坏性操作确认、限制非法输入的控件、减少错误的智能默认值、防歧义标签、自动保存和草稿恢复。

| 分数 | 标准 |
|---|---|
| 0 | 极易出错且没有护栏 |
| 1 | 少量保护，大多数输入未验证 |
| 2 | 常见错误可拦截，边界情况遗漏 |
| 3 | 多数错误路径被主动阻止 |
| 4 | 智能约束使错误几乎不可能发生 |

##### 6. 识别优于回忆

降低记忆负担，使对象、操作和选项可见或易取。检查可见选项、上下文帮助、最近项目与历史、自动补全和建议、图标文字标签。

| 分数 | 标准 |
|---|---|
| 0 | 严重依赖记忆路径和命令 |
| 1 | 多数靠回忆，功能隐藏且提示少 |
| 2 | 主操作可见，次要功能仍隐藏 |
| 3 | 大部分可发现，记忆要求很少 |
| 4 | 一切可发现，用户无需记忆 |

##### 7. 使用灵活性与效率

为专家提供不干扰新手的加速器。检查常用操作快捷键、界面定制、最近项与收藏、批量操作，以及不增加基础复杂度的高级能力。

| 分数 | 标准 |
|---|---|
| 0 | 只有一条僵硬路径 |
| 1 | 主路径之外几乎没有选择 |
| 2 | 有少量快捷方式和基础键盘支持 |
| 3 | 有良好加速器、键盘导航和部分定制 |
| 4 | 多路径、高级功能与定制都很成熟 |

##### 8. 美观且极简的设计

每个可见元素都应有用途，不能让无关或极少使用的信息争夺注意力。检查逐步所需信息、视觉层级、有目的的色彩与强调、装饰杂乱和布局焦点。

| 分数 | 标准 |
|---|---|
| 0 | 所有元素同等争夺注意力，令人不堪重负 |
| 1 | 杂乱，难以找到重点 |
| 2 | 主内容清晰但周边嘈杂 |
| 3 | 基本干净聚焦，有少量视觉噪声 |
| 4 | 完美克制，每个元素都配得上它的像素 |

##### 9. 帮助用户识别、诊断并恢复错误

错误信息应使用平实语言，准确指出问题并给出建设性解决方案。检查是否避免面向用户的错误码、具体定位问题、提供可执行恢复建议、靠近错误源展示且不清空表单。

| 分数 | 标准 |
|---|---|
| 0 | 错误晦涩、只有代码/术语或完全无提示 |
| 1 | 只有“出了问题”等模糊提示 |
| 2 | 问题说清楚了，但没有修复方法 |
| 3 | 清晰识别问题并给出下一步 |
| 4 | 精确定位、建议修复并保留用户工作 |

##### 10. 帮助与文档

即使系统无需文档也能使用，帮助仍应易找、面向任务且简洁。检查可搜索文档、上下文帮助、按任务组织、可扫描内容，以及无需离开当前上下文即可访问。

| 分数 | 标准 |
|---|---|
| 0 | 完全没有帮助 |
| 1 | 帮助难找或无关 |
| 2 | 有 FAQ/文档等基础帮助，但不在上下文中 |
| 3 | 文档可搜索且基本面向任务 |
| 4 | 在正确时刻提供正确的上下文帮助 |

---

#### 得分汇总

满分 40（10 项 × 4）。36–40 为优秀，仅需精修；28–35 为良好，应补弱项；20–27 为可接受，但用户满意前需显著改进；12–19 为较差，核心体验需要大修；0–11 为严重，当前不可用，需重新设计。

存在 `n/a` 时，最高分低于 40，按百分比而非原始分数套用区间：90%+ 优秀，70%+ 良好，50%+ 可接受，30%+ 较差，更低为严重。例如 24/32 = 75%，评级为良好。

---

#### 问题严重度（P0–P3）

| 优先级 | 名称 | 描述 | 操作 |
|---|---|---|---|
| **P0** | 阻断 | 完全无法完成任务 | 立即修复，是发布阻断项 |
| **P1** | 重大 | 引发显著困难或困惑 | 发布前修复 |
| **P2** | 次要 | 令人烦恼但存在绕过方式 | 下一轮修复 |
| **P3** | 精修 | 值得修但无实际用户影响 | 时间允许时处理 |

不确定等级时，问：“用户会因此联系支持吗？”若会，至少是 P1。

### 基于 Persona 的设计测试

从五种不同用户原型观察界面。每个 Persona 都会暴露单一“设计总监”视角遗漏的失败模式。按界面选择最相关的 2–3 个，让他们走完主要操作，报告具体风险而非泛泛担忧。

---

#### 1. 急躁的高级用户：“Alex”

熟悉同类产品，追求效率，讨厌手把手指导；会寻找捷径，否则离开。他会跳过 onboarding、寻找快捷键、尝试批量与自动化，并厌恶低风险操作的冗余步骤。

检查：能否在 60 秒内完成核心任务；常用操作有无快捷键；onboarding 能否完全跳过；弹窗能否用 Esc 关闭；是否有批量操作等高级路径。风险包括强制教程、主操作不能键盘完成、不可跳过的慢动画、适合批量却逐项处理、低风险动作反复确认。

---

#### 2. 困惑的新用户：“Jordan”

从未使用此类产品，每一步都需要指导，宁可放弃也不愿猜。他会仔细读说明、对陌生控件犹豫、不断寻找帮助、误解术语，并按字面理解标签。

检查：5 秒内能否看出首个操作；图标是否有文字；决策点有无上下文帮助；术语是否假设先验知识；每步有无返回/撤销。风险包括纯图标导航、未解释的术语、没有可见帮助、操作后下一步模糊、成功后没有确认。

---

#### 3. 依赖无障碍能力的用户：“Sam”

使用 VoiceOver/NVDA 或仅键盘导航，也可能低视力、行动受限或有认知差异。他按顺序 Tab，依赖 ARIA 与标题结构，看不到 hover 或纯视觉信号，需要至少 4.5:1 对比度，并可能放大到 200%。

检查：主要流程能否全键盘完成；交互元素是否可聚焦且焦点清晰；图片有无有意义 alt；文字对比度是否满足 WCAG AA；加载、成功、错误等状态变化是否被读屏播报。风险包括只有点击的交互、缺失焦点、仅以颜色传意、无标签字段/按钮、不可延长的限时操作、破坏读屏流程的自定义组件。

---

#### 4. 主动压力测试者：“Riley”

有条理地越过 happy path，测试边界、意外输入和体验缺口。他会尝试空状态、超长字符串、特殊字符、emoji、RTL 和 Excel 粘贴，也会后退、流程中刷新、多标签打开，并核对 UI 承诺与实际结果。

检查：0 项、1000 项和超长文本时如何；错误能否恢复；中途刷新是否保存状态；是否有表面可用却产出错误结果的功能；如何处理意外输入。风险包括静默失败、暴露技术细节或破坏界面的错误处理、无指导的空状态、刷新/导航丢数据，以及相似操作行为不一。

---

#### 5. 分心的移动用户：“Casey”

在路上单手使用手机，经常中断，网络可能较慢。偏好拇指可达的底部操作，在应用间切换，注意力和耐心有限，尽量少输入、更多点击选择。

检查：主操作是否位于屏幕下半部拇指区；离开再返回是否保留状态；3G 下是否可用；表单是否有自动补全与智能默认值；触控目标是否至少 44×44pt。风险包括顶部不可达操作、切换后丢进度、本可选择却要求长文本、每页重复加载重资源，以及触控目标太小或过密。

---

#### 选择 Persona

| 界面类型 | 主要 Persona | 原因 |
|---|---|---|
| 落地页 / 营销 | Jordan、Riley、Casey | 第一印象、信任、移动端 |
| Dashboard / 管理后台 | Alex、Sam | 高级效率、无障碍 |
| 电商 / 结账 | Casey、Riley、Jordan | 移动端、边界情况、清晰度 |
| Onboarding 流程 | Jordan、Casey | 困惑、中断 |
| 数据密集 / 分析 | Alex、Sam | 效率、键盘导航 |
| 表单密集 / 向导 | Jordan、Sam、Casey | 清晰度、无障碍、移动端 |

#### 项目专用 Persona

若 `{{config_file}}` 包含由 `impeccable init` 生成的 `## Design Context`，从受众与品牌信息派生 1–2 个额外 Persona：读取目标受众描述；找出五个预设未覆盖的主要原型；按下列模板创建：

```
##### [Role]: "[Name]"

**Profile**: [2-3 key characteristics derived from Design Context]

**Behaviors**: [3-4 specific behaviors based on the described audience]

**Red Flags**: [3-4 things that would alienate this specific user type]
```

只有存在真实 Design Context 数据时才生成专用 Persona。不得虚构受众细节；无上下文时使用五个预设 Persona。
