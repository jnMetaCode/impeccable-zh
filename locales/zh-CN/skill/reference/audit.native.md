对原生应用（`ios` / `android` / `adaptive`）执行系统化的**技术**质量检查，并生成完整报告。不要修复问题；记录问题，交给其他命令处理。

这是代码级审计，不是设计评审。从源码（SwiftUI / UIKit / Compose / React Native / Flutter）审计；浏览器工具和 `impeccable detect` 均不适用。按照平台参考评分： [ios.md](ios.md) / [android.md](android.md)，`adaptive` 同时使用两者。如果 Setup 尚未读取，评分前先读取。报告骨架与 [audit.md](audit.md) 对齐；修改时保持同步。

## 诊断扫描

全面检查 5 个维度，并按以下标准分别评分 0～4。

### 1. 无障碍（VoiceOver / TalkBack）

**检查**：
- **缺少标签**：交互元素没有无障碍标签、trait/role 或状态播报
- **阅读与焦点顺序**：遍历不合逻辑、控件不可达、导航后焦点丢失
- **文字缩放**：固定 point 破坏 Dynamic Type（iOS），或使用 px 而非 sp（Android）；大字号时布局裁切或重叠
- **触控目标**：小于 44 pt（iOS）/ 48 dp（Android），或间距过小
- **忽略 Reduce Motion**：视差和大幅滑动没有交叉淡化替代
- **对比度**：浅色或深色外观中文字对比度不达标

**评分 0～4**：0=屏幕阅读器不可用；1=重大缺口；2=部分支持但顺序或缩放失效；3=良好，仅少量问题；4=优秀，标签、顺序、缩放和 Reduce Motion 均完整

### 2. 性能

**检查**：
- **启动缓慢**：首帧前执行繁重工作
- **列表未虚拟化**：长内容没有 FlatList / LazyColumn / List 复用
- **主线程卡顿**：滚动或手势路径执行同步工作，在 60/120 Hz 下掉帧
- **浪费渲染**：React Native 不必要重渲染或 Compose 不必要重组；缺少 memoization/key
- **图片处理**：缩略图解码完整尺寸图片，且没有缓存
- **应用体积**：JS bundle 或二进制臃肿，存在未使用依赖

**评分 0～4**：0=处处卡顿；1=重大问题；2=部分达标；3=良好，可小幅改进；4=优秀，启动快、滚动顺、体积精简

### 3. 外观与主题

**检查**：
- **硬编码颜色**：使用原始 hex，而不是语义系统色（iOS）、Material 色彩角色（Android）或设计 token
- **深色外观损坏**：缺少深色变体、深色对比度差或简单反色
- **Dynamic Color**（Android 12+）：缺少静态回退，或适合使用时被忽略
- **偏离平台的材质**：应该使用系统 material 或色调层级时自行实现视觉材质

**评分 0～4**：0=全部硬编码；1=几乎没有 token；2=有 token 但使用不一致；3=良好，仅少量硬编码；4=优秀，全程语义化且两种外观均为一等方案

### 4. 平台一致性（关键）

依据已加载的平台参考及其粗糙感测试评分。**检查**：
- **系统手势损坏**：禁用 iOS 边缘返回，或劫持 Android predictive Back
- **违反 inset**：内容位于刘海、灵动岛、Home 指示条、状态栏或键盘下方
- **偏离平台的导航**：自定义全局导航、过载 tab bar、跨平台照搬模式
- **Web 形态控件**：HTML 式按钮、自定义开关、依赖 hover 的可供性
- **图标漂移**：混合图标集，而不是 SF Symbols / Material Symbols
- **系统漂移**：重复捷径或装饰模式与产品、平台或既有设计系统冲突

**评分 0～4**：0=纯 Web 移植；1=严重违反 3～4 类；2=存在 1～2 类明显问题；3=大致一致，仅细微问题；4=完全原生，熟练用户信任每个页面

### 5. 适应性

**检查**：
- **拉伸的手机布局**：平板/iPad 只放大手机界面，没有使用 size classes / window size classes
- **方向损坏**：横屏裁切、被忽略或无理由锁定
- **键盘/IME 处理**：输入框被键盘遮挡，没有调整 inset
- **多任务**：iPad Split View / Android 多窗口破坏布局
- **折叠屏**：Android 姿态变化时布局不知道铰链位置

**评分 0～4**：0=只支持一种屏幕尺寸；1=横屏或平板严重损坏；2=部分支持；3=良好，仅边缘问题；4=优秀，适配各种尺寸、方向和窗口模式

### 按严重度列出详细发现

每个问题标记 **P0～P3 严重度**：
- **P0 阻塞**：阻止任务完成，立即修复
- **P1 重大**：造成显著困难或违反平台规范，发布前修复
- **P2 次要**：令人困扰但有替代方案，下一轮修复
- **P3 精修**：可修可不修，对用户没有实质影响，有时间再处理

- **[P?] 问题名称**
- **位置**：页面、文件、行号

- **影响**：如何影响用户
- **规范**：违反的 HIG / Material 规则（如适用）
- **建议**：如何修复
- **建议命令**：使用哪个命令（优先：{{available_commands}}）

## 建议操作

按优先级列出建议命令（先 P0，再 P1，然后 P2）：

1. **[P?] `{{command_prefix}}command-name`**：简要说明（引用审计发现的具体上下文）
2. **[P?] `{{command_prefix}}command-name`**：简要说明（具体上下文）

**规则**：只能推荐以下命令：{{available_commands}}。把发现映射到最合适的命令。如果推荐了任何修复，最后一步必须是 `{{command_prefix}}impeccable polish`。

展示摘要后，告诉用户：

> 你可以让我逐项执行、一次全部执行，或按你希望的任意顺序执行。
>
> 修复后重新运行 `{{command_prefix}}impeccable audit`，查看分数是否提高。

**重要要求**：全面但可执行。过多 P3 会制造噪音，应聚焦真正重要的问题。

**绝对不要**：
- 报告问题却不解释影响
- 提供泛泛建议，必须具体且可执行
- 跳过正面发现
- 忘记排优先级，不可能所有问题都是 P0
- 未经验证就报告误报
