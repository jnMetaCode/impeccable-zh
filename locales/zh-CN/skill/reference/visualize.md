# Visualize：方向稿与资源生产

在以视觉稿驱动的构建中，且图像生成可用（执行环境原生工具可用，或 API 回退由 `impeccable context` 报告）时，从 [new-work.md](new-work.md) 加载本文件。代码驱动契约按设计跳过本文件，这不是流程漂移；此时不要加载。PRODUCT.md 与 DESIGN.md 是前置条件。new-work 已确定视觉世界，本文件不得重新开启身份探索。如果界面范围的结构轮次已经向用户展示三张可视化卡片（new-work.md 的既有世界流程），则本轮已经完成：锁定卡片中的视觉稿就是获批稿，记录批准后直接进入“批准之后”，不要重新生成。

探索稿用于检验构图、叙事、层级、密度、焦点时刻、标志性元素和图像需求，不是第二次身份工作坊。固定 DESIGN.md 的配色、字体方向、材质语言、组件性格、图像立场和动效语法。

## 生成三个构图选项

视觉稿轮次运行在构建阶段状态内：首张图生成前，必须已执行 `impeccable build-phase start --direction <seed key> --kind <...>`（roll 输出会给出命令），并打开 `comps` 阶段。阶段启动前生成的稿件不属于状态机，从那里恢复的会话也没有后续阶段可循。启动前，`impeccable generate-image` 会拒绝写入 `.impeccable/mocks/`；执行环境原生图像工具也必须遵守同样顺序。

为目标界面制作三张有明显差异的高保真北极星视觉稿，保存至 `.impeccable/mocks/`，使其跨会话保留。按界面真实视口构图：原生应用或移动优先界面使用设备尺寸的纵向画布，其他界面使用桌面横向画布；把手机界面做成横向稿会在实现前就歪曲构图。视觉稿是当前构建线程自己的工作，永不委派：写 prompt 的线程掌握方向的完整上下文，也必须在构建开始时见过每张稿。使用工作区相对路径打开每张图；沙箱查看器会拒绝绝对路径，而项目根目录下的资源都有相对路径。

基于真实内容和已经与用户讨论过的界面概念制作视觉稿。若采用既有视觉世界，每张稿都要锚定真实身份：截取代表性现有页面作为参考图，通过执行环境图像工具的输入图或 `impeccable generate-image --ref` 传入。Prompt 先描述新界面的结构，参考图负责传递配色、字体和组件性格；单靠 DESIGN.md 文字容易漂移，像素参照不会。明确参考图应贡献什么、不得贡献什么：沿用 chrome、配色、字体和组件性格；不沿用参考页面自身内容，逐字照搬 banner、hero 或 card 是参考泄漏，而非忠实。

必须有三张：一张会诱发草率盖章，三张之间的差异才能显露值得实现的构图。选中卡片的决策稿作为三张中的第一张：它已按本规范以完整保真度表达该方向，所以只需再生成两张，改变第一张固定的变量。后两张从方向文字出发，不能把第一张作为输入图，否则参考图会锚死布局，使三张坍缩成同一构图。每一张都要比第一张走得更远，而不是更干净：在同一世界里更大胆，让材质承担更多页面结构（仍遵守下述深度规则，只保留一个主导动作），使用更大或更陌生的焦点，或尝试同类产品通常不会采用的构图。把第一张简化得更整齐不构成新选择。三张必须一起送到批准点。只有本轮没有决策稿（降级 roll、身份模式页面，或方向未经过决策轮即被固定）时，才在这里生成全部三张。

- 视觉稿是设计好的界面，不是主题插图。Prompt 开头先写界面自身结构：依次列出区域及其尺度关系。没有导航的页面应明确说明没有导航，不常规界面要明确写出其非传统骨架。以氛围开头会得到小品画：模型画出鱼市，而不是鱼市网站。视觉世界可以承载页面，但不能取代页面：立面、卷帘门或书可以成为页面赖以构成的介质；若整个视口只是一张立面、封面或旅行海报，没有可工作的部分，那只是世界的图片，不是网站。
- 材质覆盖必须充分：视觉世界的材质应成为地面和主要表面，其字体塑造标题；若只在中性模板上贴一点世界的强调色，得到的只是类别默认模板加贴纸。覆盖并不等于让每个区域都表演概念；下述深度规则限制表演区域，其余区域在该世界的材质中安静工作。两个极端都会抹掉方向：纯绘制海报，以及通用产品页（标题、说明、按钮，下方一排等宽卡片）。发到手中的构图决定骨架，第二、第三稿也必须经受同一测试：左右分栏 hero（文案一边、产品另一边、下方徽标行）或居中标题加卡片行，无论换什么外观都仍是模板。
- 视觉世界承载页面部件，但不得吞掉部件。无论部件被放在哪里，页面仍须像页面一样工作：嵌入立面的导航读起来像链接，卷帘门上的文案仍是访客可读文字，门牌上的操作明显可点击，文字与背景保持可读，章节有稳定垂直节奏，主要操作清晰，下一区域确实开始新章节而不是继续作画。修复“海报化”时，应让部件在视觉世界赋予的位置上可工作，而不是搬回标准布局并铺上世界颜色；若封面变成姜黄色背景上“文案 + 设备”，封面概念已经丢失。
- 当视觉世界是一个物件时，页面只在一个尺度、一个视角下展示这一个物件，并保持真实形态：书只能沿一条书脊展开两页，不能凭空出现第三块；承载导航的书脊属于页面中的这本书，不能另放一本书。更多内容应进入物件自身表面或下方下一跨页，不能复制物件或制造不可能的折叠。页面本身要铺满画布边缘，不要画浏览器窗口、地址栏、设备或桌面；Prompt 应描述页面，而非浏览器截图。每次渲染都自检：如果它可以直接挂成海报，或像一张加了文字的照片，就不是视觉稿。重新生成，并明确写出既定构图的区域，让部件在原位工作。
- 反向失败同样严重：界面中完全没有主题内容。主题应作为各区域承载的内容出现；视觉世界装扮框架，但不能取代框架展示的东西。删除主题通常来自 prompt 的排除列表，因此排除项只应约束杜撰的事实；禁止某种媒介必须源于已承诺的图像立场，而不能只因谨慎。接受稿件前，要能指出主题在哪里。若图像描绘了视觉世界的一切，却没有目标主题，无论氛围多忠实都失败；按区域明确主题内容后重新生成。
- 把视觉稿当成最终上线屏幕评判：仅凭图像就必须能读出访客任务。无需说明文字，直接从稿件说出界面模式；若无法说出，这是只有艺术指导、没有界面。以访客任务作为 prompt 主轴重新生成。
- 视觉世界的覆盖深度取决于界面模式。Persuade 或 Experience 界面可让世界按上述方式主导并组织页面。Operate 或 Read 界面中，访客是来使用屏幕的，因此视觉世界只通过材质、字体、颜色、密度和一个标志动作进入；所有控件都必须是用户熟悉的真实 Web 组件：button、tab、input、select、filter、带可排序表头的 table，以及看起来就是导航的 navigation。不要把世界自身的界面当服装套上去，例如终端功能键栏或命令提示符、仪器边框、用账本横线冒充表格。工程师无法用标准 Web 组件构建的视觉稿只是工具的图片，而非工具本身。
- 投入感来自深度，不来自多个区域同时表演。视觉世界通过一个主导动作及支撑它的材质、字体和间距进入；其余区域安静地承载信息，使主动作清晰。一个区域只在世界语法中履行职责，比表演概念更能延伸方向。此检查只削弱竞争，不删内容：被安静化的区域保留信息但停止表演；页面仍以真实阅读字号（1440px 宽页面正文约 16px）承载导航方式、产品价值、支撑文案、操作和下一部分预览。这只是内容清单，不是布局；每项位置由构图决定。若第二个元素以同等尺度与指定焦点竞争，稿件就在喊叫；没有指定焦点而多个区域同时表演，也是同一种喊叫。保留最强动作、让其他区域安静后重新生成。繁忙只是更吵，不是更大胆。
- 用户入围多个概念时，把三张稿分布到这些概念中。
- 已确定单一方向时，改变图像能够解决的结构不确定性：拓扑、顺序、密度、层级、焦点构图或交互框架。
- 展示足够多的首屏以下内容，证明概念能统领整个界面。
- 不要生成配色样本，不要重新提问氛围，不要引入不同字体声音，也不要发明新图案。若已承诺的视觉世界无法支撑概念，应返回概念候选列表，而非改变视觉世界。

每张视觉稿都是方向测试，不是像素截图规范。核心 UI 文字、响应式行为、无障碍、语义和交互状态仍由实现负责。

## 唯一批准点

在决策页面上同时展示三张稿（`impeccable serve-question`，每张稿作为一个选项的主视觉）；只有执行环境能内联显示图片时才可直接在其中展示。纯文本界面不算展示。询问哪些部分应保留、哪些部分不符合视觉世界，以及选中概念应批准、组合、修改还是拒绝。然后停止并等待。结构化模拟用户也视为有人参与，必须收到同样问题。

用户批准方向或明确授权你代选之前，不得开始编码。若用户授权代选，依据任务简报、PRODUCT.md 和 DESIGN.md 作出选择，并说明证据。批准会细化任务概念，但不会修改 DESIGN.md。

此批准点没有替代品，也没有跳过条件。结构化提问工具失败时，退回决策页面；只有二者都失败后才能把选择视为已授权，并且必须像正常批准一样准确记录，在第一条回复而非最后一条才披露代选。最终评审会把“视觉稿轮次有稿件但无批准记录”视为实质问题；`.impeccable/mocks/decision/` 下的决策稿只是方向轮次发到手中的牌，不属于本轮输出，也不自动表示批准。

批准后，把选择记录在工具可发现的位置：在界面简报写入获批稿路径，并在对应 `.json` prompt sidecar 中加入 `"approved": true`（每个由 `impeccable generate-image` 生成的视觉稿都有 sidecar；使用原生工具时若没有就创建）。Sidecar 会随 mocks 目录移动，使批准信息跨会话、跨机器保留，即使对方看不到简报；`impeccable build-phase advance` 也靠它关闭 comps 阶段。总结构图和稿件中不得被字面实现的部分，返回 new-work.md，从获批概念记录方向契约，然后开始构建。

## 批准之后：视觉稿成为规范

获批稿是转换为语义化、响应式、无障碍代码的北极星，但绝不授权重新构图：保留配色和情绪却重画拓扑，就是第二次艺术指导。不得把核心 UI 文字或控件栅格化。未经询问，不得在批准后替换视觉驱动力。

对稿件内容必须测量，而非凭记忆。new-work.md 第 6 节按阶段执行构建（`impeccable build-phase`）：spec 阶段把视觉稿转为带采样配色的区域框（`impeccable comp-spec`）。每个区域的媒介由像素实际内容决定，不能按“什么容易实现”决定：人物、产品物体、机器、有透视/明暗/绘画技巧的插画，以及任何明确纹理（编织布、纸张颗粒、织物、皮革、拉丝金属），都属于 `plate` / `image` / `texture` 区域，必须以栅格交付；文字、控件、chrome、元素可数的图表、平面形状系统，以及需要运动、缩放或响应的内容，才是语义元素。

把雕塑感面板的质感标成“CSS”，或用多顶点 `clip-path` 模拟撕裂边缘，是对获批设计的隐性删除；检测器的 organic-clip-path、buried-raster 规则以及 hero gate 的区域评分会捕获它。放弃图像原生区域属于范围决策，只能由用户在批准点作出，不能在批准后静默压平。生成图像是一种材质，不是事实主张：证据规则约束事实陈述、规格、推荐语和被呈现为真实的照片，不约束渲染保真度。

## 图像板与来源

每个栅格区域的 plate 必须在任何页面代码之前，于 plates 阶段由随附的资源生产 Agent 或当前线程生成。使用 `impeccable comp-spec --crop <id>`，并把 `impeccable comp-spec --plate-prompt <id>` 保存为 prompt 文件；将裁剪图和 prompt 交给执行环境图像工具，或运行 `impeccable generate-image --ref <crop.png> --prompt-file <prompt.txt> --out <plate.png> --size <WxH> --quality high`。

孤立抠图需在 plate-prompt 与 API 生成命令中都加入 `--background transparent`；使用原生 PNG alpha，并保留白色绘制区域和透明空隙。全幅图像使用 `--background opaque`。先创建输出目录，再分别在亮、暗背景上检查 alpha。

生成上下文是资源的一部分。使用任何工具生成图像后，执行 `{{scripts_path}}/impeccable embed-prompt <image> --prompt "<prompt>"`，传入工具实际收到的精确字符串（`impeccable generate-image` 会自动完成）。`--read` 可恢复 prompt，`--scan <dir>` 可列出仍缺少 prompt 的栅格图。内嵌 prompt 与该区域在 spec 中的记录共同构成栅格图的**来源证据**，产物引用的每张栅格图都必须带有它；来自素材库或既有文件的图则嵌入来源。之后在修复批次或评审重建中创建、替换的栅格图也遵守同一流程；修复中弃用的图在同一批次删除。

使用启动时 `impeccable context` 在 IMAGE_TOOLS 行报告的转换器处理图片。只有它报告没有工具时才探测，且每会话最多探测一次，不能每张图重复探测。
