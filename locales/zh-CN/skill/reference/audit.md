执行系统化的**技术**质量检查并生成完整报告。不要修复问题；记录问题，交给其他命令处理。

这是代码级审计，不是设计评审。检查实现中可以测量和验证的内容。

**仅适用于 Web。** 原生平台（`ios` / `android` / `adaptive`）应改用 [audit.native.md](audit.native.md)；如果项目是原生应用，立即切换。

## 诊断扫描

全面检查 5 个维度，并按以下标准分别评分 0～4。

### 1. 无障碍（A11y）

**检查**：
- **对比度问题**：文字对比度低于 4.5:1（AAA 为 7:1）
- **动态效果敏感性**：`prefers-reduced-motion` 需要有意设计的替代方案，同时保留状态变化和层级；标记会破坏有用反馈的全局 `0.01ms` 动画清除、超过阈值的闪烁，以及阻碍焦点、阅读或任务完成的动效
- **缺少 ARIA**：交互元素没有正确的 role、label 或 state
- **键盘导航**：缺少焦点指示器、Tab 顺序不合理或存在键盘陷阱
- **语义化 HTML**：标题层级错误、缺少 landmark、使用 div 代替 button
- **Alt 文字**：图片说明缺失或质量差
- **表单问题**：输入框没有标签、错误提示不清楚、缺少必填标记

**评分 0～4**：0=不可访问（未通过 WCAG A）；1=重大缺口；2=部分支持但仍有显著缺口；3=良好，基本达到 WCAG AA；4=优秀，完整达到 WCAG AA 并接近 AAA

### 2. 性能

**检查**：
- **布局抖动**：在循环中交替读取和写入布局属性
- **昂贵动画**：随意动画化布局属性、无边界的 blur/filter/shadow，或明显掉帧的效果
- **缺少优化**：图片未延迟加载、资源未优化
- **滥用 will-change**：大范围应用或静止时仍保留 `will-change`；它只应用于已知的昂贵动画，不是基础要求
- **Bundle 大小**：不必要的 import、未使用依赖
- **渲染性能**：不必要的重新渲染、缺少 memoization

**评分 0～4**：0=问题严重；1=重大问题；2=部分优化但仍有缺口；3=良好，可小幅改进；4=优秀，快速、精简且优化充分

### 3. 主题

**检查**：
- **硬编码颜色**：颜色没有使用设计 token
- **深色模式损坏**：缺少深色变体或深色主题对比度差
- **Token 不一致**：使用错误 token 或混用 token 类型
- **主题切换问题**：切换主题时某些值不更新

**评分 0～4**：0=没有主题系统；1=几乎全部硬编码；2=有 token 但使用不一致；3=良好，仅少量硬编码；4=优秀，token 系统完整且深色模式完全正常

### 4. 响应式设计

**检查**：
- **固定宽度**：硬编码宽度导致移动端损坏
- **触控目标**：交互元素小于 44×44px
- **触控交互损坏**：自定义 slider、拖动区域和可滚动控件条的主要手势在触控下失效、吞掉页面滚动、拖动被页面滚动夺走，或手势中断后保持卡住。代码迹象包括只处理鼠标、pointer 拖动区域没有 `touch-action`、cancel、失去 capture 或 blur 时没有清理拖动状态。浏览器工具能模拟触控时应实际执行手势；渲染视口只能证明布局，不能证明手势。说明证据来自模拟视口、合成触控、哪个引擎或真机，并指出哪些内容尚未测试
- **水平滚动**：窄视口出现内容溢出
- **文字缩放**：增大字号后布局损坏
- **缺少断点**：没有移动端或平板变体

**评分 0～4**：0=仅桌面可用；1=重大问题；2=移动端可用但粗糙；3=良好，仅少量触控目标或溢出问题；4=优秀，所有视口流畅，触控目标正确且手势真实可用

### 5. 实现完整性（关键）

运行随附检测器，并结合上下文验证每项发现。寻找重复的实现捷径、设计系统漂移、误导或纯装饰内容，以及可与无关产品互换的结构。把确定性发现与视觉判断分开，并明确指出误报。

**评分 0～4**：0=系统性漂移；1=重复出现重大失败；2=存在若干经验证的问题；3=仅有孤立的小问题；4=连贯且有明确意图

### 按严重度列出详细发现

每个问题标记 **P0～P3 严重度**：
- **P0 阻塞**：阻止任务完成，立即修复
- **P1 重大**：造成显著困难或违反 WCAG AA，发布前修复
- **P2 次要**：令人困扰但有替代方案，下一轮修复
- **P3 精修**：可修可不修，对用户没有实质影响，有时间再处理

每个问题记录：
- **[P?] 问题名称**
- **位置**：组件、文件、行号
- **类别**：无障碍 / 性能 / 主题 / 响应式 / 实现完整性
- **影响**：如何影响用户
- **WCAG/标准**：违反的标准（如适用）
- **建议**：如何修复
- **建议命令**：使用哪个命令（优先：{{available_commands}}）

### 模式与系统性问题

识别代表系统缺口而非一次性错误的重复问题，例如：
- “15 个以上组件出现硬编码颜色，应使用设计 token”
- “整个移动端体验中的触控目标普遍小于 44px”

### 正面发现

记录做得好的实践，以便保持和复用。

## 建议操作

按优先级列出建议命令（先 P0，再 P1，然后 P2）：

1. **[P?] `{{command_prefix}}command-name`**：简要说明（引用审计发现的具体上下文）
2. **[P?] `{{command_prefix}}command-name`**：简要说明（具体上下文）

**规则**：只能推荐以下命令：{{available_commands}}。把发现映射到最合适的命令。如果推荐了任何修复，最后一步必须是 `{{command_prefix}}impeccable polish`。

展示摘要后，告诉用户：

> 你可以让我逐项执行、一次全部执行，或按你希望的任意顺序执行。
>
> 修复后重新运行 `{{command_prefix}}impeccable audit`，查看分数是否提高。

**重要要求**：全面但可执行。过多 P3 会制造噪音，应聚焦真正重要的问题。

**绝对不要**：
- 报告问题却不解释影响
- 提供泛泛建议，必须具体且可执行
- 跳过正面发现
- 忘记排优先级，不可能所有问题都是 P0
- 未经验证就报告误报
