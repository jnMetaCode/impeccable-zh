用色彩建立层级、含义和氛围。保留已经确认的品牌和语义惯例；不要以增加色彩为名替换整个视觉世界。

## 访客模式

- **Persuade + Experience：** 当所选视觉世界需要时，色彩可以承载语气并占据大面积区域。
- **Operate + Read：** 色彩主要编码操作、选择、状态、导向和阅读层级。强调色越少见，力量越强。

## 选择前先审计

阅读 DESIGN.md、token、资源、当前主题和代表性状态。识别：

- 哪些颜色是已经确认的品牌承诺；
- 当前表面、文字、操作和语义角色；
- 灰度导致层级或状态不清的位置；
- 对比度失败和仅靠颜色传达的信息；
- 浅色或深色模式以及数据可视化要求；
- 任务需要更多颜色，还是需要新的视觉身份。

如果需要新视觉身份，使用 [new-work.md](new-work.md)。只有无法推断具有约束力的品牌决策时才询问。

## 选择策略

编辑前明确预期情绪温度、主导关系、对比范围和用色剂量。策略可以克制，也可以沉浸，但必须服从简报和所选视觉世界，而不是固定百分比规则。

建立角色，而不是堆积色板：

- 画布和抬升表面；
- 主要与次要文字；
- 操作、焦点和选择；
- 边框和分隔线；
- 成功、警告、错误和信息；
- 必要时的数据类别或尺度。

使用项目现有色彩空间。新的 Web 色板优先使用 OKLCH，因为它能可预测地调整明度和色度。根据产品含义和视觉方向选择色相，绝不要依赖品类默认联想。

## 在系统尺度上应用

- 让最强的颜色占据一个明确区域或角色，而不是散落微小强调色。
- 让主要操作容易被找到；不要把它的颜色浪费在装饰上。
- 只有品牌色相确实能增强凝聚力时才给中性色染色。只要符合视觉世界，中性灰完全有效。
- 在彩色表面上，根据前景色或表面色相推导次要文字，不要使用褪色的通用灰。
- 保持语义含义一致，但应尊重平台和领域惯例，不要假设固定色相。
- 数据不能只靠颜色编码，还应使用不同的明度、色度、形状、标签或图案。
- 深色模式应显式设计表面层级和对比度，不要机械反转浅色主题。
- 项目存在 token 系统时，定义基础值和语义 token。主题变化通常应重新映射语义角色。

与层级、状态、内容或视觉世界没有关系的装饰不构成色彩策略。

## 对比度与感知

验证计算后的前景色与背景色组合：

| 内容 | WCAG AA 最低要求 |
|---|---|
| 正文 | 4.5:1 |
| 大号文字 | 3:1 |
| 控件、图标、焦点指示器 | 3:1 |

不要只依赖肉眼判断。检查交互状态、浮层、图片上的文字、禁用内容和两种主题。模拟常见色觉缺陷。用颜色传达的信息还需要文字、形状、图标或位置作为辅助。

推导 OKLCH 色阶时，应改变明度，并在接近白色和黑色时降低色度。不要为了数学上的整齐，在极端明度下维持高色度。当透明度会使对比度依赖上下文时，优先使用明确颜色，而不是层层叠加半透明色。

## 验证

- 每种颜色都有稳定角色或视觉世界特有的氛围用途。
- 注意力落在预期操作、内容或状态上。
- 色板适用于安静、密集、交互、错误和空状态。
- 浅色和深色主题都经过独立构图，而非机械反转。
- 所有相关状态的对比度和非颜色提示均达标。
- 结果能明确属于该产品，而不是通用的“多彩”处理。

色板的存在有充分理由后，交给 `{{command_prefix}}impeccable polish` 完成最终精修。

## Live 模式签名参数

从 Live 模式调用时，每个变体都声明一个 `color-amount` 参数。基于 `var(--p-color-amount, 0.5)` 编写 CSS，使用户无需重新生成，就能从中性状态调到该变体完整的色彩策略。

```json
{"id":"color-amount","kind":"range","min":0,"max":1,"step":0.05,"default":0.5,"label":"Color amount"}
```

最多添加两个变体专属参数，例如色板、温度或染色行为。遵循 [live.md](live.md) 的参数契约。
