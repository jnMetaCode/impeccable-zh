佈局把產品優先順序轉化為閱讀順序、分組、節奏和可用空間。移動元素前，先診斷結構問題。

## 訪客模式

- **Persuade + Experience：** 當所選視覺世界有充分理由時，構圖可以不對稱、流動或有意打破常規。
- **Operate + Read：** 可預測的結構、穩定的密度和易於導航的線性順序本身就是可供性。
- **原生平臺：** 按照 [ios.md](ios.md) 或 [android.md](android.md) 處理導航、安全邊距、調整和觸控目標。

保留既有視覺世界。layout 命令只改變其中的結構；替換視覺身份屬於 [new-work.md](new-work.md)。

## 兩項獨立評估

如果子 Agent 工具可用且獲准使用，應獨立執行以下兩項評估；否則按順序自行完成。

1. **佈局評估：** 檢查有代表性的狀態和視口，並用渲染結果或原始碼證據回答每個問題：
   - **閱讀順序：** 使用眯眼測試。模糊細節後，是否仍能依次識別主要元素、次要元素和主要分組？
   - **分組：** 相關專案是否彼此接近、不同分組是否充分分離，還是依靠容器彌補薄弱的鄰近關係？
   - **節奏：** 緊湊與寬鬆的間隔是否形成有意節奏，還是重複一種間距直到所有內容權重相同？
   - **結構：** 拓撲是否符合內容和任務？重複卡片、分欄或區塊真的等價，還是僅僅來自框架預設值？
   - **密度：** 每個區域的資訊量是否符合使用頻率、決策複雜度和訪客模式？
   - **調整：** 在窄屏、中間寬度、寬屏、縮放和在地化狀態下，哪些內容會重排、摺疊、換行、滾動或固定？DOM 與焦點順序是否仍和視覺順序一致？
   - **極端情況：** 長內容、空狀態、浮層、粘性元素、安全區域和較小觸控目標是否暴露結構缺陷？
2. **機械掃描：** 執行：

```bash
{{scripts_path}}/impeccable detect --json --scope layout [target files or dirs]
```

同時檢查偵測器無法判斷的任意間距、溢位、層疊和容器行為。第一項評估中不要混入機械掃描證據，編輯前再綜合兩輪結果。乾淨的掃描結果不能證明層級或節奏正確。

## 確立空間主張

編輯前明確：

- 主要閱讀或任務路徑；
- 哪些內容屬於一組，哪些必須分開；
- 哪個元素主導，哪個提供支援；
- 預期密度和間距節奏；
- 結構如何隨容器、視口、輸入方式和內容極值變化。

選擇能夠表達這些關係的最簡單結構模型。根據佈局原語所控制的關係使用它們，並用語義化名稱定義可複用的間距和容器角色。

## 應用

- 按含義分組。新增容器或裝飾前先使用鄰近關係。
- 透過緊湊與寬鬆間隔之間有意的對比創造節奏。
- 使用有文件的間距尺度，不使用一次性數值。以 4 為基礎通常能提供僅使用 8 倍數時缺少的實用中間檔。
- 讓層級服從產品優先順序，而不是框架預設值。
- 讓不同內容在視覺上保持區別，但不要把每個分組都變成孤立元件。
- 讓回應式行為改變結構：根據仍然重要的內容重排、摺疊、重流或揭示。
- 同一組件出現在不同情境時，優先使用能感知容器的元件。
- 當 `gap` 比子元素 margin 更直接地表達同級關係時，使用 `gap`。
- 即使可見標記很小，也要保持觸控目標可用。
- 只有在能澄清狀態或層級時才使用縱深。
- 檢查實際渲染結果後再做視覺校正。

變化本身不是目標。重複應幫助識別；只有內容或優先順序變化時才打破重複。

## 驗證

- 眯眼測試仍能依次顯示主要元素、次要元素和主要分組。
- 閱讀和任務路徑在每個受支援尺寸下都保持清晰。
- 相關內容自然成組，無關內容不會混在一起。
- 緊湊與寬鬆間距形成有意節奏，而不是單調重複。
- 密度符合使用頻率和內容複雜度。
- 長文字、空狀態、在地化、縮放和動態內容不會破壞結構。
- 鍵盤、觸控和輔助技術順序與視覺順序一致。
- 最終機械掃描不存在無法解釋的問題。

逐項用渲染或原始碼證據回答，然後重新執行掃描。不要用一句“是”代替驗證。

結構穩定後，交給 `{{command_prefix}}impeccable polish`。

## Live 模式簽名參數

每個變體都宣告一個粗粒度 `density` 參數，並基於 `var(--p-density, 1)` 編寫間距。

```json
{"id":"density","kind":"range","min":0.6,"max":1.4,"step":0.05,"default":1,"label":"Density"}
```

只有拓撲確實出現分支時，才能再新增一個結構參數。遵循 [live.md](live.md) 的參數契約。
