# Visualize：方向稿與資源生產

在以視覺稿驅動的建置中，且影像產生可用（執行環境原生工具可用，或 API 回退由 `impeccable context` 報告）時，從 [new-work.md](new-work.md) 載入本檔案。程式碼驅動契約按設計跳過本檔案，這不是流程漂移；此時不要載入。PRODUCT.md 與 DESIGN.md 是前置條件。new-work 已確定視覺世界，本檔案不得重新開啟身份探索。如果介面範圍的結構輪次已經向使用者展示三張視覺化卡片（new-work.md 的既有世界流程），則本輪已經完成：鎖定卡片中的視覺稿就是獲批稿，記錄批准後直接進入“批准之後”，不要重新產生。

探索稿用於檢驗構圖、敘事、層級、密度、焦點時刻、標誌性元素和影像需求，不是第二次身份工作坊。固定 DESIGN.md 的配色、字型方向、材質語言、元件性格、影像立場和動效語法。

## 產生三個構圖選項

視覺稿輪次執行在建置階段狀態內：首張圖產生前，必須已執行 `impeccable build-phase start --direction <seed key> --kind <...>`（roll 輸出會給出命令），並開啟 `comps` 階段。階段啟動前產生的稿件不屬於狀態機，從那裡恢復的會話也沒有後續階段可循。啟動前，`impeccable generate-image` 會拒絕寫入 `.impeccable/mocks/`；執行環境原生影像工具也必須遵守同樣順序。

為目標介面製作三張有明顯差異的高保真北極星視覺稿，儲存至 `.impeccable/mocks/`，使其跨會話保留。按介面真實視口構圖：原生應用或移動優先介面使用裝置尺寸的縱向畫布，其他介面使用桌面橫向畫布；把手機介面做成橫向稿會在實作前就歪曲構圖。視覺稿是目前建置執行緒自己的工作，永不委派：寫 prompt 的執行緒掌握方向的完整上下文，也必須在建置開始時見過每張稿。使用工作區相對路徑開啟每張圖；沙箱檢視器會拒絕絕對路徑，而專案根目錄下的資源都有相對路徑。

基於真實內容和已經與使用者討論過的介面概念製作視覺稿。若採用既有視覺世界，每張稿都要錨定真實身份：擷取代表性現有頁面作為參考圖，透過執行環境影像工具的輸入圖或 `impeccable generate-image --ref` 傳入。Prompt 先描述新介面的結構，參考圖負責傳遞配色、字型和元件性格；單靠 DESIGN.md 文字容易漂移，畫素參照不會。明確參考圖應貢獻什麼、不得貢獻什麼：沿用 chrome、配色、字型和元件性格；不沿用參考頁面自身內容，逐字照搬 banner、hero 或 card 是參考洩漏，而非忠實。

必須有三張：一張會誘發草率蓋章，三張之間的差異才能顯露值得實作的構圖。選中卡片的決策稿作為三張中的第一張：它已按本規範以完整保真度表達該方向，所以只需再產生兩張，改變第一張固定的變數。後兩張從方向文字出發，不能把第一張作為輸入圖，否則參考圖會錨死佈局，使三張坍縮成同一構圖。每一張都要比第一張走得更遠，而不是更乾淨：在同一世界裡更大膽，讓材質承擔更多頁面結構（仍遵守下述深度規則，只保留一個主導動作），使用更大或更陌生的焦點，或嘗試同類產品通常不會採用的構圖。把第一張簡化得更整齊不構成新選擇。三張必須一起送到批准點。只有本輪沒有決策稿（降級 roll、身份模式頁面，或方向未經過決策輪即被固定）時，才在這裡產生全部三張。

- 視覺稿是設計好的介面，不是主題插圖。Prompt 開頭先寫介面自身結構：依次列出區域及其尺度關係。沒有導航的頁面應明確說明沒有導航，不常規介面要明確寫出其非傳統骨架。以氛圍開頭會得到小品畫：模型畫出魚市，而不是魚市網站。視覺世界可以承載頁面，但不能取代頁面：立面、捲簾門或書可以成為頁面賴以構成的介質；若整個視口只是一張立面、封面或旅行海報，沒有可工作的部分，那只是世界的圖片，不是網站。
- 材質覆蓋必須充分：視覺世界的材質應成為地面和主要表面，其字型塑造標題；若只在中性模板上貼一點世界的強調色，得到的只是類別預設模板加貼紙。覆蓋並不等於讓每個區域都表演概念；下述深度規則限制表演區域，其餘區域在該世界的材質中安靜工作。兩個極端都會抹掉方向：純繪製海報，以及通用產品頁（標題、說明、按鈕，下方一排等寬卡片）。發到手中的構圖決定骨架，第二、第三稿也必須經受同一測試：左右分欄 hero（文案一邊、產品另一邊、下方徽標行）或居中標題加卡片行，無論換什麼外觀都仍是模板。
- 視覺世界承載頁面部件，但不得吞掉部件。無論部件被放在哪裡，頁面仍須像頁面一樣工作：嵌入立面的導航讀起來像連結，捲簾門上的文案仍是訪客可讀文字，門牌上的操作明顯可點選，文字與背景保持可讀，章節有穩定垂直節奏，主要操作清晰，下一區域確實開始新章節而不是繼續作畫。修復“海報化”時，應讓部件在視覺世界賦予的位置上可工作，而不是搬回標準佈局並鋪上世界顏色；若封面變成薑黃色背景上“文案 + 裝置”，封面概念已經丟失。
- 當視覺世界是一個物件時，頁面只在一個尺度、一個視角下展示這一個物件，並保持真實形態：書只能沿一條書脊展開兩頁，不能憑空出現第三塊；承載導航的書脊屬於頁面中的這本書，不能另放一本書。更多內容應進入物件自身表面或下方下一跨頁，不能複製物件或製造不可能的摺疊。頁面本身要鋪滿畫布邊緣，不要畫瀏覽器視窗、位址列、裝置或桌面；Prompt 應描述頁面，而非瀏覽器截圖。每次渲染都自檢：如果它可以直接掛成海報，或像一張加了文字的照片，就不是視覺稿。重新產生，並明確寫出既定構圖的區域，讓部件在原位工作。
- 反向失敗同樣嚴重：介面中完全沒有主題內容。主題應作為各區域承載的內容出現；視覺世界裝扮框架，但不能取代框架展示的東西。刪除主題通常來自 prompt 的排除列表，因此排除項只應約束杜撰的事實；禁止某種媒介必須源於已承諾的影像立場，而不能只因謹慎。接受稿件前，要能指出主題在哪裡。若影像描繪了視覺世界的一切，卻沒有目標主題，無論氛圍多忠實都失敗；按區域明確主題內容後重新產生。
- 把視覺稿當成最終上線螢幕評判：僅憑影像就必須能讀出訪客任務。無需說明文字，直接從稿件說出介面模式；若無法說出，這是隻有藝術指導、沒有介面。以訪客任務作為 prompt 主軸重新產生。
- 視覺世界的覆蓋深度取決於介面模式。Persuade 或 Experience 介面可讓世界按上述方式主導並組織頁面。Operate 或 Read 介面中，訪客是來使用螢幕的，因此視覺世界只通過材質、字型、顏色、密度和一個標誌動作進入；所有控制元件都必須是使用者熟悉的真實 Web 元件：button、tab、input、select、filter、帶可排序表頭的 table，以及看起來就是導航的 navigation。不要把世界自身的介面當服裝套上去，例如終端功能鍵欄或命令提示符、儀器邊框、用賬本橫線冒充表格。工程師無法用標準 Web 元件建置的視覺稿只是工具的圖片，而非工具本身。
- 投入感來自深度，不來自多個區域同時表演。視覺世界透過一個主導動作及支撐它的材質、字型和間距進入；其餘區域安靜地承載資訊，使主動作清晰。一個區域只在世界語法中履行職責，比表演概念更能延伸方向。此檢查只削弱競爭，不刪內容：被安靜化的區域保留資訊但停止表演；頁面仍以真實閱讀字號（1440px 寬頁面正文約 16px）承載導航方式、產品價值、支撐文案、操作和下一部分預覽。這只是內容清單，不是佈局；每項位置由構圖決定。若第二個元素以同等尺度與指定焦點競爭，稿件就在喊叫；沒有指定焦點而多個區域同時表演，也是同一種喊叫。保留最強動作、讓其他區域安靜後重新產生。繁忙只是更吵，不是更大膽。
- 使用者入圍多個概念時，把三張稿分佈到這些概念中。
- 已確定單一方向時，改變影像能夠解決的結構不確定性：拓撲、順序、密度、層級、焦點構圖或互動框架。
- 展示足夠多的首屏以下內容，證明概念能統領整個介面。
- 不要產生配色樣本，不要重新提問氛圍，不要引入不同字型聲音，也不要發明新圖案。若已承諾的視覺世界無法支撐概念，應返回概念候選列表，而非改變視覺世界。

每張視覺稿都是方向測試，不是畫素截圖規範。核心 UI 文字、回應式行為、無障礙、語義和互動狀態仍由實作負責。

## 唯一批准點

在決策頁面上同時展示三張稿（`impeccable serve-question`，每張稿作為一個選項的主視覺）；只有執行環境能內聯顯示圖片時才可直接在其中展示。純文字介面不算展示。詢問哪些部分應保留、哪些部分不符合視覺世界，以及選中概念應批准、組合、修改還是拒絕。然後停止並等待。結構化模擬使用者也視為有人參與，必須收到同樣問題。

使用者批准方向或明確授權你代選之前，不得開始編碼。若使用者授權代選，依據任務簡報、PRODUCT.md 和 DESIGN.md 作出選擇，並說明證據。批准會細化任務概念，但不會修改 DESIGN.md。

此批准點沒有替代品，也沒有跳過條件。結構化提問工具失敗時，退回決策頁面；只有二者都失敗後才能把選擇視為已授權，並且必須像正常批准一樣準確記錄，在第一條回覆而非最後一條才披露代選。最終評審會把“視覺稿輪次有稿件但無批准記錄”視為實質問題；`.impeccable/mocks/decision/` 下的決策稿只是方向輪次發到手中的牌，不屬於本輪輸出，也不自動錶示批准。

批准後，把選擇記錄在工具可發現的位置：在介面簡報寫入獲批稿路徑，並在對應 `.json` prompt sidecar 中加入 `"approved": true`（每個由 `impeccable generate-image` 產生的視覺稿都有 sidecar；使用原生工具時若沒有就建立）。Sidecar 會隨 mocks 目錄移動，使批准資訊跨會話、跨機器保留，即使對方看不到簡報；`impeccable build-phase advance` 也靠它關閉 comps 階段。總結構圖和稿件中不得被字面實作的部分，返回 new-work.md，從獲批概念記錄方向契約，然後開始建置。

## 批准之後：視覺稿成為規範

獲批稿是轉換為語義化、回應式、無障礙程式碼的北極星，但絕不授權重新構圖：保留配色和情緒卻重畫拓撲，就是第二次藝術指導。不得把核心 UI 文字或控制元件柵格化。未經詢問，不得在批准後替換視覺驅動力。

對稿件內容必須測量，而非憑記憶。new-work.md 第 6 節按階段執行建置（`impeccable build-phase`）：spec 階段把視覺稿轉為帶取樣配色的區域框（`impeccable comp-spec`）。每個區域的媒介由畫素實際內容決定，不能按“什麼容易實作”決定：人物、產品物體、機器、有透視/明暗/繪畫技巧的插畫，以及任何明確紋理（編織布、紙張顆粒、織物、皮革、拉絲金屬），都屬於 `plate` / `image` / `texture` 區域，必須以柵格交付；文字、控制元件、chrome、元素可數的圖表、平面形狀系統，以及需要運動、縮放或響應的內容，才是語義元素。

把雕塑感面板的質感標成“CSS”，或用多頂點 `clip-path` 模擬撕裂邊緣，是對獲批設計的隱性刪除；偵測器的 organic-clip-path、buried-raster 規則以及 hero gate 的區域評分會捕獲它。放棄影像原生區域屬於範圍決策，只能由使用者在批准點作出，不能在批准後靜默壓平。產生影像是一種材質，不是事實主張：證據規則約束事實陳述、規格、推薦語和被呈現為真實的照片，不約束渲染保真度。

## 影像板與來源

每個柵格區域的 plate 必須在任何頁面程式碼之前，於 plates 階段由隨附的資源生產 Agent 或目前執行緒產生。使用 `impeccable comp-spec --crop <id>`，並把 `impeccable comp-spec --plate-prompt <id>` 儲存為 prompt 檔案；將裁剪圖和 prompt 交給執行環境影像工具，或執行 `impeccable generate-image --ref <crop.png> --prompt-file <prompt.txt> --out <plate.png> --size <WxH> --quality high`。

孤立摳圖需在 plate-prompt 與 API 產生命令中都加入 `--background transparent`；使用原生 PNG alpha，並保留白色繪製區域和透明空隙。全幅影像使用 `--background opaque`。先建立輸出目錄，再分別在亮、暗背景上檢查 alpha。

產生上下文是資源的一部分。使用任何工具產生影像後，執行 `{{scripts_path}}/impeccable embed-prompt <image> --prompt "<prompt>"`，傳入工具實際收到的精確字串（`impeccable generate-image` 會自動完成）。`--read` 可恢復 prompt，`--scan <dir>` 可列出仍缺少 prompt 的柵格圖。內嵌 prompt 與該區域在 spec 中的記錄共同構成柵格圖的**來源證據**，產物引用的每張柵格圖都必須帶有它；來自素材庫或既有檔案的圖則嵌入來源。之後在修復批次或評審重建中建立、替換的柵格圖也遵守同一流程；修復中棄用的圖在同一批次刪除。

使用啟動時 `impeccable context` 在 IMAGE_TOOLS 行報告的轉換器處理圖片。只有它報告沒有工具時才探測，且每會話最多探測一次，不能每張圖重複探測。
