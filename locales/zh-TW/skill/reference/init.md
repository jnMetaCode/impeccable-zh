# Init 流程

`init` 把穩定的產品事實記錄到 PRODUCT.md。它不虛構視覺體系，也不寫 DESIGN.md；[new-work.md](new-work.md) 負責建立或擴充功能視覺體系，[document.md](document.md) 負責記錄已有體系。可執行的現有 Web 專案還可能獲得 `.impeccable/live/config.json`。

## 第 1 步：載入目前狀態

使用 `impeccable context` 解析出的 PRODUCT.md 路徑。應更新該檔案，不能建立另一個相互競爭的事實源。子應用繼承根目錄上下文時，寫入前確認哪些內容共享、哪些只屬於該應用。

- **沒有 PRODUCT.md：** 探索專案、訪談使用者並建立檔案。
- **已有 PRODUCT.md：** 只詢問哪些產品知識已經過時或缺失；沒有理由時不要重新討論已確認欄位。
- **舊版 PRODUCT.md：** 只補充缺失的穩定事實；沒有 `## Platform` 時預設視為 `web`，除非證據表明不是。
- **只有 DESIGN.md：** 不修改它，另行建立 PRODUCT.md。
- **重設計或品牌升級請求：** 除非使用者改變事實，否則保留已確認的產品資訊。視覺替換稍後在 new-work 中進行，不在 init 完成。

絕不能靜默覆蓋已有檔案，也不要在 init 中主動提供 DESIGN.md。如果 init 是由另一項請求觸發，完成 PRODUCT.md 後繼續原請求。新的視覺工作進入 new-work；`shape` 則先恢復它自己的任務訪談。

## 第 2 步：探索專案

提問前先掃描足夠的資訊，避免讓使用者重複儲存庫已經回答的內容：產品文件與文案；package/config 和應用邊界；功能、工作流、路由和角色；名稱、Logo、法律/證明素材和品牌承諾；平臺與無障礙訊號；需要即時模式時還包括開發命令和入口。

儲存庫證據只能作為假設，不能當作使用者批准。可以記錄視覺成熟度，但不要在這裡描述、擴充功能或替換視覺體系。

形成平臺假設：`web`、`ios`、`android` 或 `adaptive`。`adaptive` 指同一個產品確實針對不同作業系統調整設計語言。移動網頁仍然是 `web`；網站外套原生殼並不會讓它自動擁有原生設計語言。

## 第 3 步：訪談產品事實

{{ask_instruction}} 只詢問原始請求和儲存庫強證據都無法回答、且會實質影響結果的問題。

有結構化提問工具時使用它，否則提出問題並等待。每輪最多三個聚焦問題；建立新的 PRODUCT.md 前，至少需要一輪真實回答或批准。對推斷內容進行確認。

是否有人能回答必須透過實際機制判斷，不能靠猜測：提問工具或目前工具介面的決策頁可以證明存在回答渠道；系統提示聲稱使用者無人值守，並不能證明本會話沒人。先用真實的第一輪問題探測一次。只有探測報錯或超時後，才能根據明確簡報進行推斷；此時必須在 PRODUCT.md 中逐項標註推斷，並在第一次回覆而不是最後一次回覆中說明使用了替代方式。

先處理最會改變未來產品決策的未知項：

1. 主要使用者是誰、處於什麼情境、正在完成什麼任務？
2. 產品讓什麼成為可能，它真正不同的機制或定位是什麼？
3. 未來工作必須保留哪些穩定約束、資產、證據或產品事實？

平臺含糊時單獨確認。如果專案沒有框架或腳手架且請求暗示要建置產品，技術棧屬於使用者決策，不屬於你的預設決定：詢問一次他們希望使用靜態 HTML/CSS、指定框架還是接受你的推薦，並確認會限制選擇的部署目標。把結果寫入 `## Stack`；如果使用者把選擇委託給你，寫明 `delegated`，讓後續工作知道你確實提供過選擇。只有受眾、品牌承諾、證據或無障礙存在實質缺口時才增加一輪。未決定的事實應明確記錄，不能自行編造。

init 期間不要詢問審美方向、情緒感受、視覺參考、顏色、排版或風格。如果使用者主動提供具有約束力的視覺要求，只記錄，不展開。

### 應當記錄的內容

- 使用者、任務、工作流、目的、成功標準、定位和使用情境；
- 能力、約束、術語、證據、平臺和無障礙；
- 已確認的語氣、資產和品牌承諾。

### 不應記錄的內容

- 視覺體系、配色、排版、元件或頁面概念；
- 訪客模式、敘事、CTA/證據順序等介面策略；
- 編造的客戶評價、客戶名單、基準、價格、許可證或部署宣告；
- 強迫使用者決定每個可選欄位的要求。

## 第 4 步：寫入 PRODUCT.md

只寫已經確認的事實和明確標記的開放決策。無關章節直接省略，不要用空泛文字填滿。

```markdown
# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Stack
[僅用於全新專案：記錄使用者對技術棧問題的回答，例如 “static HTML/CSS”“Astro” 或 “delegated: <你的選擇和原因>”。現有程式碼已經明確技術棧時省略。]

## Users
[主要使用者、使用情境和任務。只有已確認時才加入其他受眾。]

## Product Purpose
[產品做什麼、為什麼存在、怎樣算成功。]

## Positioning
[相鄰產品無法如實複製的產品機制或主張。]

## Operating Context
[使用或評估產品時真實存在的工作流、環境、工具、文件、材料和習慣。]

## Capabilities and Constraints
[已確認的功能、技術約束、術語，以及明確尚未決定的產品事實。]

## Brand Commitments
[已有名稱、語氣、資產、個性、身份約束，以及使用者明確指定為約束的參考。沒有時省略。]

## Evidence on Hand
[真實內容、資料、示範、評價、案例、媒體或資產；適用時給出路徑。明確未來工作不得編造的缺失證據。]

## Product Principles
[由確認答案匯出的 3～5 條穩定戰略原則，不寫視覺配方。]

## Accessibility & Inclusion
[已知使用者需求或強制標準。沒有產品特定要求時省略。]
```

Platform 必須是裸值 `web`、`ios`、`android` 或 `adaptive`。保留有價值的舊版標題。新檔案寫到 `PROJECT_ROOT/PRODUCT.md`，否則更新 context 解析出的檔案。任何視覺體系或介面概念工作之前必須先寫入該檔案。

逐字複製 `impeccable:product-schema` 註釋，更新舊檔案時也一樣。它記錄產品檔案遵循的 schema 版本，讓後續版本能區分“有意保持簡短的檔案”和“在某章節出現前寫成的舊檔案”，避免讓使用者重複已經完成的訪談。只有本引用中的模板版本變化時才更新數字。後續版本廢棄的章節會在啟動時報告；經使用者同意後刪除，不要長期攜帶。

如果剛記錄的平臺是 `ios`、`android` 或 `adaptive`，在任何設計工作前載入 [ios.md](ios.md)、[android.md](android.md) 或兩者。原來沒有 PRODUCT.md 時，`impeccable context` 無法知道平臺，因此不會載入它們；init 是首次獲得該答案的地方。

### 完成門禁

載入 new-work 或恢復 shape/build 前，確認 PRODUCT.md 已存在於解析路徑幷包含已確認的產品檔案。檔案不存在就表示 init 未完成。不能用訪談筆記、規劃材料或後續設計文字代替它。

## 第 5 步：記錄工作流預設值

當影像產生可用且尚未記錄 `buildPath` 時，詢問一次新介面採用哪種建置方式。可用是指宿主原生影像工具，或 `impeccable context` 報告為 `IMAGE_GEN_AVAILABLE` 的 API 回退。宿主原生工具不會出現在啟動輸出中，因此支援影像產生的宿主沒有輸出，並不表示無需詢問。這必須是獨立問題，不能附在另一問題中。技術棧問題問“用什麼建置”，本問題問“從哪裡開始建置”，前一個答案不代表使用者同意後一個選擇。

在使用者實際看到的問題中說明權衡，因為初次接觸者不理解兩個名稱：**comp-first**（先用影像設定品質標準，再寫程式碼；構圖更大膽，但更慢，最終實作必須匹配影像）或 **code-first**（直接建置；把設計野心寫入方向契約並在收尾時稽核；更輕、更快）。

把答案合併寫入 `.impeccable/config.json`，值為 `"buildPath": "comp"` 或 `"buildPath": "code"`。只能寫使用者實際選擇的值。你的推薦不是使用者回答；根據沉默寫入的值會成為無人確認的長期預設設定，與“只問一次”的目標相反。

問題無人回答時不記錄任何內容，並用一句話說明本會話採用哪條路徑以及它沒有被儲存。在影像產生可用且沒有記錄值時，new-work 預設採用 comp-first；應明確說出它，不能靜默選擇更保守的方案。未設定是有效工作狀態，不是缺陷：決策頁開關控制單次會話，使用者首次主動切換時，new-work 的一次性提示才記錄答案。設定是唯一事實源。它是工作流設定而不是產品事實，絕不能複製進 `## Stack` 或 PRODUCT.md 的其他章節。

`.impeccable/config.json` 或被 Git 忽略的 `.impeccable/config.local.json` 中已有值就是已確認答案：再次執行時靜默遵守，不要重複詢問。它是預設值而非鎖定值；決策頁可以為單次會話切換且不會寫回。沒有影像產生時無需選擇，只能使用 code-first。

然後在適合時設定即時模式：原生或不可執行專案跳過，已有設定保持不變。其他情況遵循 [live.md](live.md) 的首次設定流程。任何 CSP 原始碼修改仍需按該流程取得同意。

## 第 6 步：結束或恢復原任務

總結已經記錄和有意保持未決定的事實。不要只因缺少 DESIGN.md 就主動提出建立它。

根據真實專案狀態推薦下一步：

- 空專案或早期專案：自然詢問要建置哪個介面；使用者只想確認簡報而不實作時使用 `/impeccable shape <surface>`。只有請求確實需要時，new-work 才建立視覺體系。
- 已有一致介面但沒有 DESIGN.md：使用者希望獨立記錄現有系統時使用 `/impeccable document`。
- 已有介面需要改進：指出範圍最準確的相關命令。
- 已設定並適合視覺迭代的 Web 專案：使用 `/impeccable live`。

如果 init 由另一個請求觸發，完成後直接恢復原任務，不要重新執行 `impeccable context`。上面載入的原生平臺引用是原 context 唯一無法提供的資訊；後續視覺決策由 new-work 負責。
