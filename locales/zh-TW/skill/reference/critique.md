### 目的

解析出一個穩定目標，執行兩項相互獨立的評估，綜合形成設計評審，持久化快照，並詢問使用者下一步要改進什麼。聊天回覆是主要交付物；快照只是本輪歸檔。

### 硬性不變數

- 評估 A（設計評審）和評估 B（偵測器/瀏覽器證據）都必須執行。
- 只要環境提供 sub-agent/Task 工具，A、B 就必須由兩個隔離的 sub-agent 執行。在目前上下文內序列執行雖然“可行”，但不被允許，屬於降級執行。只有沒有 sub-agent 工具時（或會請求授權的環境中使用者拒絕時）才可內聯。
- 任何原因導致降級時，報告第一行必須是：`⚠️ DEGRADED: single-context (<reason>)`。靜默降級等於評審失敗。
- A 必須在偵測器發現進入父級綜合上下文之前完成。偵測器輸出雖是確定性的，仍會錨定判斷。
- 除非 `impeccable detect` 缺失或真實嘗試後崩潰，否則跳過偵測器即為失敗。
- 目標可檢視且瀏覽器檢查可用時，必須檢查瀏覽器。
- 只為評審視覺化啟動的本地服務必須後台執行，記錄停止方法，並在最終報告前停止，除非使用者要求保持執行。
- 只有指令碼注入成功且偵測器確實在頁面執行，才能聲稱存在使用者可見 overlay。
- 問題必須是回覆的最後內容。先寫完報告再提問，之後不得追加內容；結構化提問後的文字會被扣留到使用者回答，導致報告看起來未執行。
- 一輪執行若既沒有針對性問題，也沒有字面行 `Questions skipped: <reason>`，就是未完成。報告不是終點，閉環才是。

### 設定

1. **解析目標**為具體檔案路徑或 URL。二者指向同一介面時優先原始碼路徑：埠會漂移，路徑不會。
   - “首頁” → `site/pages/index.astro` 或 `index.html`
   - “設定彈窗” → 主要元件檔案
   - “此頁面” → 目前 URL 或原始碼檔案
2. **確認目標可產生規範 slug**：
   ```bash
   {{scripts_path}}/impeccable critique-storage slug "<resolved-path-or-url>"
   ```
   後續命令也接受解析後的目標並內部產生同一 slug；不要手寫 slug。若命令非零退出，本輪跳過持久化和趨勢，但繼續評審。
3. 若 `.impeccable/critique/ignore.md` 存在則讀取。靜默刪除匹配的發現；這是 critique 唯一會消費的歷史執行輸入。

### 評估編排

把 A、B 委派給不同 sub-agent，雙方不得看到彼此輸出。綜合前不得向使用者展示發現。

所有執行環境的 sub-agent 門禁：
- 除非下方環境專用門禁覆蓋，否則只要暴露 sub-agent/Task 工具，就並行產生兩個隔離 agent；這是強制預設行為，不能為了快而內聯。
- “不可用”只表示會話沒有暴露 sub-agent/Task 工具（或會詢問的環境中使用者拒絕），不表示使用不方便。
- 僅在 sub-agent 不可用時依次執行：完成並記錄 A，再執行 B，最後綜合並輸出降級橫幅。
- 無論採用哪條路徑，都要在報告頭宣告。跳過 sub-agent 又不顯示橫幅是最常見的失敗。

<codex>
Codex sub-agent 門禁（覆蓋上述預設門禁；Codex 權限模型要求產生前徵詢）：
- 詢問是正常路徑，不算降級。使用者同意並產生 agent 後屬於雙 agent 路徑，不能僅因詢問而顯示降級橫幅。
- 若暴露 `spawn_agent`，且使用者明確允許 sub-agent、委派或並行工作，立即產生 A、B。
- 若暴露 `spawn_agent` 但使用者未明確允許，只問一次：“Impeccable critique is designed to run two independent sub-agents for an unanchored assessment. May I use sub-agents for this critique?”然後停止等待。
- 使用者同意則產生；拒絕則序列執行，報告以 `⚠️ DEGRADED: single-context (sub-agents declined by user)` 開頭。
- 未暴露 `spawn_agent` 時不要詢問，序列執行並使用 `⚠️ DEGRADED: single-context (spawn_agent unavailable in this session)`。
- 獲准後產生失敗，則序列執行並使用 `⚠️ DEGRADED: single-context (sub-agent spawn failed: <exact error>)`。
優先使用 `fork_context: false`，以自包含 prompt 提供 cwd、目標、Live URL、參考資料、產品上下文和輸出契約。若使用 `fork_context: true`，省略 `agent_type`、`model`、`reasoning_effort`。
</codex>

瀏覽器自動化可用時，每項評估各自建立新標籤頁。即使已有標籤頁正位於目標 URL，也不得複用。

### 評估 A：設計評審

讀取相關原始碼；瀏覽器自動化可用時目視檢查頁面。以設計總監視角思考。

評估：
- **設計特異性**：構圖、互動和視覺語言是否紮根於本產品，還是換成無關產品也成立？必須在看到偵測器輸出前判斷。
- **整體設計**：層級、資訊架構、情感契合、可發現性、構圖、排版、顏色、無障礙、狀態、文案和邊界情況。
- **認知負荷**：參考下文[認知負荷評估](#cognitive-load-assessment)，報告清單失敗項和可見選項超過 4 個的決策點。
- **情感旅程**：峰終定律、情緒低谷、高風險時刻的安撫。
- **Nielsen 啟發式**：參考下文[啟發式評分指南](#heuristics-scoring-guide)，對 10 項各打 0–4 分；模式適用性規則允許不適用的項標記 `n/a`，不能強行評分。

返回：設計特異性結論、啟發式得分、認知負荷、情感旅程、2–3 個優點、3–5 個優先問題、Persona 風險、次要觀察和啟發性問題。

### 評估 B：偵測器 + 瀏覽器證據

執行內建偵測器並收集瀏覽器視覺化證據。B 是必需項，在 A、B 都結束前必須與 A 隔離。

CLI 掃描：
```bash
{{scripts_path}}/impeccable detect --json [target]
```

- 標記檔案/目錄作為 `[target]` 傳入；不要傳純 CSS 檔案。
- URL 跳過 CLI 掃描，使用瀏覽器視覺化。
- 超大目錄（500+ 個可掃描檔案）應縮小範圍或詢問使用者。
- 退出碼 0 表示無發現，2 表示有發現。
- 偵測器入口缺失或載入失敗時，報告“確定性掃描不可用”，繼續瀏覽器/人工評審。

當目標可檢視且瀏覽器自動化可用時，必須做瀏覽器視覺化。本地檔案使用 localhost 開發/靜態 URL；除非瀏覽器明確支援此流程，否則避免 `file://`。Overlay 流程：

1. 新建標籤頁並導航。優先使用環境原生/browser-canvas 截圖路徑；只有沒有原生瀏覽器工具時才自寫 Playwright/Puppeteer 指令碼。
2. 透過設定 `document.title` 並追加 `<script>` 標籤，預檢可變注入能力。只讀 evaluate API 不算。
3. 無法修改時，跳過 Live 服務、瀏覽器展示和注入，報告回退訊號。
4. 可以修改時，啟動 `{{scripts_path}}/impeccable live-server --background`，環境支援則展示瀏覽器，標記 `[Human]`，滾到頂部，注入 `http://localhost:PORT/detect.js`，等待 2–3 秒，讀取 `impeccable` console 訊息，然後停止 Live 服務。
5. 多檢視目標應選 3–5 個代表頁面注入。

<codex>
Codex Browser 注意：使用 Browser skill。不要浪費一次 Browser 嘗試開啟 `file://`。只有確認可變指令碼注入成功後，才為 `[Human]` overlay 路徑呼叫 `visibility.set(true)`，並用 `get()` 驗證。使用 `tab.dev.logs({ filter: "impeccable" })` 獲取 console 結果。其 Playwright `evaluate(...)` 表面只讀，不得依靠它修改頁面。
</codex>

返回：CLI 發現的 JSON/計數、適用時的瀏覽器 console 發現、誤報，以及被跳過/失敗的瀏覽器步驟與具體原因。

B 返回可用 CLI 發現後直接複用。除非 B 失敗、輸出截斷，或缺少計數、規則名、檔案位置，否則父上下文不得重跑 `impeccable detect`。

<codex>
Codex 失敗核算：最終 Run Notes 必須包含目標 slug、忽略清單、評估獨立性、CLI 偵測器、瀏覽器可見性、overlay 注入、Live 服務清理、臨時檔案清理，以及所用回退訊號。報告組裝完成後，不要再執行儲存庫狀態檢查、遲到的 API 探索或無關驗證。
</codex>

### 產生綜合評審報告

把兩項評估綜合為一份報告，不得簡單拼接。說明 LLM 評審與偵測器在哪裡一致，偵測器發現了哪些 LLM 遺漏的問題，以及哪些偵測結果是誤報。

聊天回覆是面向使用者的主要交付物。必須在聊天中完整展示下列結構化評審，不能用摘要和連結代替；持久化快照只是歸檔。

<codex>
Codex 最終回覆注意：`$impeccable critique` 會產出報告，因此最終聊天回覆應有意超過通常的簡短收尾風格。除非使用者明確只要摘要，否則不要把標題寫成“Critique Summary”。
</codex>

像設計總監一樣組織回饋：

#### 報告頭來源

第一行必須宣告評估執行方式，確保降級永不靜默：
- 雙 agent：`Method: dual-agent (A: <agent-id> · B: <agent-id>)`
- 降級：`⚠️ DEGRADED: single-context (<reason, e.g. no sub-agent tool exposed>)`

#### 設計健康分
> *參考下文[啟發式評分指南](#heuristics-scoring-guide)。*

以表格展示 Nielsen 10 項啟發式得分：

| # | Heuristic | Score | Key Issue |
|---|-----------|-------|-----------|
| 1 | Visibility of System Status | ? | [specific finding or "n/a" if solid] |
| 2 | Match System / Real World | ? | |
| 3 | User Control and Freedom | ? | |
| 4 | Consistency and Standards | ? | |
| 5 | Error Prevention | ? | |
| 6 | Recognition Rather Than Recall | ? | |
| 7 | Flexibility and Efficiency | ? | |
| 8 | Aesthetic and Minimalist Design | ? | |
| 9 | Error Recovery | ? | |
| 10 | Help and Documentation | ? | |
| **Total** | | **??/[applicable max]** | **[Rating band]** |

適用最高分等於實際評分項數量乘 4：十項全適用為 **/40**，兩項 `n/a` 時為 **/32**。部分評分絕不能仍寫 `/40`。

誠實評分。4 分意味著真正優秀；多數真實介面得分在 20–32/40。

**模式適用性**：Persuade 和 Experience 介面（著陸頁、活動頁、作品集、作品正文）可把第 7 項（靈活性與效率）和第 10 項（幫助與文件）標為 `n/a`；其他確實不適用於目前介面的項也可如此。Score 單元格寫 `n/a` 並附一行原因，按適用最高分重新歸一化總分，如兩項不適用時寫 **24/32**，使評級區間保持同比例。快照必須記錄適用最高分和 `n/a` 項。

#### 設計特異性結論

**從這裡開始。** 結果是否像為此產品專門創作，還是類別內可以互換？

**LLM assessment**：不受錨定影響的特異性判斷，覆蓋整體一致性、結構雷同、類別可互換選擇及錯失的產品性格機會。

**Deterministic scan**：概括自動偵測結果、計數和檔案位置，註明偵測器補獲的遺漏和誤報。

**Visual overlays**（注入成功時）：告知使用者 overlay 已在瀏覽器的 **[Human]** 標籤頁可見並高亮問題，概括 console 輸出。若嘗試過但注入失敗，明確說明沒有可靠的使用者可見 overlay，並報告回退訊號。

#### 整體印象
簡短直覺反應：有效之處、無效之處和唯一最大的機會。

#### 做得好的地方
列出 2–3 項，具體說明為何有效。

#### 優先問題
按重要性排列 3–5 個最有影響的問題。

每個問題標註 **P0–P3 嚴重度**（定義見[問題嚴重度](#issue-severity-p0p3)）：
- **[P?] What**：清晰命名問題
- **Why it matters**：如何傷害使用者或破壞目標
- **Fix**：具體如何修改
- **Suggested command**：可處理它的命令（只能來自 {{available_commands}}）

#### Persona 風險
> *參考下文[Persona 測試](#persona-based-design-testing)。*

根據介面型別自動選擇最相關的 2–3 個 Persona。若 `{{config_file}}` 包含由 `impeccable init` 產生的 `## Design Context`，再從受眾/品牌資訊產生 1–2 個專案專用 Persona。

讓每個 Persona 走完主要操作並列出具體風險。不要寫泛泛的 Persona 描述，而要指出具體失敗元素和互動。例如 Alex 缺少快捷鍵、主要操作需點選八次、被迫經過 onboarding；Jordan 遇到純圖示導航、技術化錯誤文案且沒有幫助。

#### 次要觀察
簡記值得處理但影響較小的問題。

#### 值得思考的問題
提出可能開啟更好方案的挑戰性問題，例如主要操作能否更突出、是否必須如此複雜、更自信的版本會是什麼樣。

<codex>
#### Run Notes
保持精簡。記錄目標 slug、忽略清單、評估獨立性、CLI 偵測器、瀏覽器可見性、overlay 注入、Live 服務和臨時檔案清理狀態。失敗或跳過的步驟需給出具體觀察原因和回退訊號。持久化完成後，最終聊天回覆還要記錄快照寫入與趨勢讀取狀態。

Run Notes 只出現在最終聊天中，不寫入快照正文，因為持久化、趨勢讀取和臨時清理發生在快照寫入後；否則歸檔會留下“等待持久化”之類的過時狀態。
</codex>

**記住**：直接、具體、同時說明問題及其使用者影響，並給出明確建議。徹底刪掉“可以考慮探索”。嚴格排序；若一切都重要，就沒有重點。不要淡化批評，開發者需要誠實回饋才能交付優秀設計。

### 交付報告

現在先把完整報告寫入聊天回覆，再做任何持久化。報告是交付物，後續只是記賬。

必須先做這一步，因為最常見的失敗是隻把報告寫進持久化 heredoc，然後以一份使用者從未讀到的完美歸檔結束。只存在於 `.impeccable/critique/` 的報告等於沒有交付。持久化也不是本輪終點；之後仍要追加趨勢和閉環問題。

### 持久化快照

報告定稿後寫入 `.impeccable/critique/`，方便使用者回看，也使 `{{command_prefix}}impeccable polish` 無需複製貼上就能讀取優先問題。若設定階段 slug 為 null（目標模糊或只是根目錄），跳過本節。

1. 把正文寫入臨時檔案再交給 helper。包含已經向使用者交付過的完整評審（啟發式表格、特異性結論、優先問題、Persona 風險、次要觀察和問題），但在後續“詢問使用者”/“建議操作”之前停止。它只是副本，不是首次交付。<codex>臨時正文不包含 Run Notes。</codex>
2. 透過 `IMPECCABLE_CRITIQUE_META` 傳入結構化元資料並寫入：
   ```bash
   IMPECCABLE_CRITIQUE_META='{"target":"<user phrasing>","total_score":<n>,"max_score":<n>,"na_heuristics":"<comma-separated numbers, or empty>","p0_count":<n>,"p1_count":<n>}' \
     {{scripts_path}}/impeccable critique-storage write "<resolved target>" <body-file>
   ```
   `max_score` 是表格的適用最高分；本地檔案還會記錄精確內容指紋。Helper 會輸出寫入的絕對路徑。保留快照檔案，由 polish 關閉，本輪不關閉。
3. 寫入嘗試結束後，無論成功與否都刪除臨時檔案。失敗時在最終輸出簡記 `temp-file cleanup failed: <reason>`，但不阻斷評審。
4. 讀取最近五次趨勢：
   ```bash
   {{scripts_path}}/impeccable critique-storage trend "<resolved target>" 5
   ```
5. 在報告後、問題前向使用者輸出一行趨勢及寫入路徑。同一最高分可只標一次；最高分不同則逐項寫分母並說明啟發式集合不同，不可直接比較。舊條目缺少 `max_score` 時按 40。首次執行明確說沒有趨勢。
6. 進入下節發出問題；若數量允許跳過，則輸出 `Questions skipped: <reason>`。未完成此閉環不算執行結束，也會讓 `{{command_prefix}}impeccable polish` 無法繼承優先問題。

這是 fire-and-forget。不要展示 helper JSON，只顯示人類可讀的趨勢和路徑。失敗不應阻斷後續流程；列印錯誤後繼續。

### 詢問使用者

**展示發現之後**，根據實際發現提出針對性問題。{{ask_instruction}} 回答將塑造行動計劃。問題必須與報告在同一訊息中，先完整報告，最後提問；不得拆成兩輪。

問題可覆蓋：基於具體發現選擇最優先類別；確認發現的語氣不匹配是否有意；在“前三項 / 全部 / 僅關鍵問題”等具體範圍中選擇；確有必要時詢問哪些區域不可改。

規則：每個問題必須引用報告的具體發現，不能泛問受眾；最多 2–4 個；提供具體選項而非開放問題。只有優先問題少於 3 個時才允許跳過。最終回覆必須包含針對性問題，或包含字面行 `Questions skipped: <reason>` 並寫明允許跳過的數量。每題有 2–3 個與發現相關的具體選項，不得只用開放式問題結尾，也不得兩者都沒有。

### 建議操作

使用者回答後，根據其選擇形成具體行動計劃。把優先問題對映到可用命令，但不要執行；使用者決定何時開始。

#### 操作摘要

按執行順序列出建議，每項都聯絡本輪發現：

1. **`{{command_prefix}}command-name`**：簡述要修復的內容，並引用評審中的具體上下文
2. **`{{command_prefix}}command-name`**：簡述具體問題與預期改進

規則：
- 只能推薦這些命令：{{available_commands}}
- 不要推薦與發現無關的命令，也不要把多個重疊命令堆在一起。
- 對每個命令說明它將處理哪些優先問題。
- 如果建議任何修復，以 `{{command_prefix}}impeccable polish` 作為最終步驟。
- 不要在未經使用者確認時自動執行建議。

最後提示：

> 修復後重新執行 `{{command_prefix}}impeccable critique`，檢視評分是否提升。

若使用者選擇開始修復，先執行最高優先順序命令，並把本報告快照作為輸入。若使用者選擇分階段處理，明確第一階段邊界。若使用者拒絕修改，保留快照，不再施壓。長期設計上下文仍是約束，不能因一次評審而改寫。

### 認知負荷評估

認知負荷是使用介面所需的全部腦力。過載會導致錯誤、挫敗和離開。本參考用於識別並修復認知過載。

---

#### 三類認知負荷

##### 內在負荷：任務本身

使用者目標固有的複雜度無法消除，但可以組織：把複雜任務拆成獨立步驟；提供模板、預設值和示例等腳手架；漸進披露目前所需內容；把相關決策歸組。

##### 外在負荷：糟糕設計

設計缺陷造成的腦力是純浪費，必須堅決消除。常見來源包括：需要使用者自行建立心智地圖的混亂導航；迫使猜測含義的模糊標籤；爭奪注意力的視覺雜亂；妨礙學習的不一致模式；使用者意圖與結果之間的無謂步驟。

##### 相關負荷：學習投入

用於建立理解的腦力是有益負荷，會帶來熟練度。用逐漸揭示覆雜性的漸進披露、獎勵學習的一致模式、確認理解正確的回饋，以及透過行動而非大段文字教學的 onboarding 來支援它。

---

#### 認知負荷清單

按以下八項評估介面：

- [ ] **單一焦點**：使用者能否不受競爭元素干擾地完成主要任務？
- [ ] **分塊**：資訊是否以易消化的小組呈現（每組 ≤4 項）？
- [ ] **歸組**：相關內容是否透過鄰近、邊框或共同背景在視覺上成組？
- [ ] **視覺層級**：螢幕上最重要的內容是否一眼可見？
- [ ] **一次一件事**：使用者能否先專注一個決策，再進入下一項？
- [ ] **最少選擇**：每個決策點的可見選項是否精簡到 ≤4 個？
- [ ] **工作記憶**：使用者是否必須記住上一屏資訊才能操作目前屏？
- [ ] **漸進披露**：複雜度是否只在需要時出現？

計數失敗項：0–1 項為低負荷（良好），2–3 項為中等（儘快處理），4 項以上為高負荷（需關鍵修復）。

---

#### 工作記憶規則

**人類工作記憶一次只能容納 ≤4 項**（Cowan 2001 對 Miller 定律的修訂）。在每個決策點，計算使用者必須同時考慮的不同選項、操作或資訊：≤4 可控；5–7 已接近邊界，應歸組或漸進披露；8+ 已過載，使用者會跳過、誤點或放棄。

實踐：操作按鈕採用 1 個主操作、1–2 個次操作，其餘收入選單；頂級導航 ≤5 項；長文保持一條閱讀路徑，把相關連結集中在末尾；文件側欄每層可見同級項 ≤4 後再歸組；作品集/畫廊每屏只要求一個決策，不同時暴露篩選、排序和標籤控制。

---

#### 常見認知負荷違規

1. **選項之牆**：一次展示 10+ 個無層級選擇。按類別歸組、突出推薦項、漸進披露。
2. **記憶橋**：完成第三步必須記住第一步內容。保持相關上下文可見，或在需要處重複。
3. **隱藏導航**：使用者必須自行建立位置地圖。始終顯示目前位置，如麵包屑、活動態和進度。
4. **術語屏障**：技術或領域術語迫使使用者翻譯。使用平實語言；不可避免的術語就地解釋。
5. **視覺噪聲底**：所有元素權重相同。建立一個主元素、2–3 個次元素，其餘弱化。
6. **模式不一致**：相似操作在不同位置行為不同。相同操作型別必須使用相同 UI 模式。
7. **多工要求**：同時要求閱讀、決策、導航。順序化步驟，一次做一件事。
8. **上下文切換**：為一個決策在螢幕、標籤或彈窗間跳轉。把所需資訊並置，減少往返。

### 啟發式評分指南

按 0–4 分評估 Nielsen 10 項可用性啟發式。4 分表示真正優秀，而非“勉強夠用”。

#### Nielsen 十項啟發式

##### 1. 系統狀態可見性

以及時、適當的回饋告知使用者發生了什麼。檢查非同步載入指示、儲存/提交/刪除確認、多步驟進度、導航目前位置和就地表單校驗。

| 分數 | 標準 |
|---|---|
| 0 | 無回饋，使用者只能猜測結果 |
| 1 | 極少回饋，大多數操作沒有可見響應 |
| 2 | 部分狀態有回饋，仍有重大缺口 |
| 3 | 大部分操作回饋清晰，只有小缺口 |
| 4 | 每個操作都有確認，進度始終可見 |

##### 2. 系統與現實世界匹配

使用使用者語言和現實慣例，以自然邏輯順序組織資訊。檢查熟悉術語、符合預期的資訊順序、可識別圖示與隱喻、適合受眾的領域語言和自然閱讀流。

| 分數 | 標準 |
|---|---|
| 0 | 全是使用者陌生的技術術語 |
| 1 | 多數內容混亂，需要領域專長才能導航 |
| 2 | 平實語言和洩漏術語混雜 |
| 3 | 基本自然，偶有術語需要上下文 |
| 4 | 始終流利地說使用者的語言 |

##### 3. 使用者控制與自由

使用者需要從非預期狀態快速逃離。檢查撤銷/重做、表單與彈窗取消、返回安全位置、清除篩選/搜尋/選擇，以及退出長流程的方式。

| 分數 | 標準 |
|---|---|
| 0 | 使用者被困，只能重新整理 |
| 1 | 出口隱蔽且難找 |
| 2 | 主流程有出口，邊界情況沒有 |
| 3 | 多數操作可退出和撤銷 |
| 4 | 所有場景都有撤銷、取消、返回與退出 |

##### 4. 一致性與標準

使用者不應猜測不同文字、情境或操作是否含義相同。檢查術語、操作結果、平臺慣例、視覺系統和互動模式是否一致。

| 分數 | 標準 |
|---|---|
| 0 | 到處不一致，像多個產品拼接 |
| 1 | 大量相似事物外觀或行為不同 |
| 2 | 主流程一致，細節分裂 |
| 3 | 基本一致，少量偏差不致混淆 |
| 4 | 系統完全統一且行為可預測 |

##### 5. 錯誤預防

優於優秀錯誤資訊的是從源頭防止錯誤。檢查破壞性操作確認、限制非法輸入的控制元件、減少錯誤的智慧預設值、防歧義標籤、自動儲存和草稿恢復。

| 分數 | 標準 |
|---|---|
| 0 | 極易出錯且沒有護欄 |
| 1 | 少量保護，大多數輸入未驗證 |
| 2 | 常見錯誤可攔截，邊界情況遺漏 |
| 3 | 多數錯誤路徑被主動阻止 |
| 4 | 智慧約束使錯誤幾乎不可能發生 |

##### 6. 識別優於回憶

降低記憶負擔，使物件、操作和選項可見或易取。檢查可見選項、上下文幫助、最近專案與歷史、自動補全和建議、圖示文字標籤。

| 分數 | 標準 |
|---|---|
| 0 | 嚴重依賴記憶路徑和命令 |
| 1 | 多數靠回憶，功能隱藏且提示少 |
| 2 | 主操作可見，次要功能仍隱藏 |
| 3 | 大部分可發現，記憶要求很少 |
| 4 | 一切可發現，使用者無需記憶 |

##### 7. 使用靈活性與效率

為專家提供不干擾新手的加速器。檢查常用操作快捷鍵、介面定製、最近項與收藏、批次操作，以及不增加基礎複雜度的高階能力。

| 分數 | 標準 |
|---|---|
| 0 | 只有一條僵硬路徑 |
| 1 | 主路徑之外幾乎沒有選擇 |
| 2 | 有少量快捷方式和基礎鍵盤支援 |
| 3 | 有良好加速器、鍵盤導航和部分定製 |
| 4 | 多路徑、高階功能與定製都很成熟 |

##### 8. 美觀且極簡的設計

每個可見元素都應有用途，不能讓無關或極少使用的資訊爭奪注意力。檢查逐步所需資訊、視覺層級、有目的的色彩與強調、裝飾雜亂和佈局焦點。

| 分數 | 標準 |
|---|---|
| 0 | 所有元素同等爭奪注意力，令人不堪重負 |
| 1 | 雜亂，難以找到重點 |
| 2 | 主內容清晰但周邊嘈雜 |
| 3 | 基本乾淨聚焦，有少量視覺噪聲 |
| 4 | 完美剋制，每個元素都配得上它的畫素 |

##### 9. 幫助使用者識別、診斷並恢復錯誤

錯誤資訊應使用平實語言，準確指出問題並給出建設性解決方案。檢查是否避免面向使用者的錯誤碼、具體定位問題、提供可執行恢復建議、靠近錯誤源展示且不清空表單。

| 分數 | 標準 |
|---|---|
| 0 | 錯誤晦澀、只有程式碼/術語或完全無提示 |
| 1 | 只有“出了問題”等模糊提示 |
| 2 | 問題說清楚了，但沒有修復方法 |
| 3 | 清晰識別問題並給出下一步 |
| 4 | 精確定位、建議修復並保留使用者工作 |

##### 10. 幫助與文件

即使系統無需文件也能使用，幫助仍應易找、面向任務且簡潔。檢查可搜尋文件、上下文幫助、按任務組織、可掃描內容，以及無需離開目前上下文即可訪問。

| 分數 | 標準 |
|---|---|
| 0 | 完全沒有幫助 |
| 1 | 幫助難找或無關 |
| 2 | 有 FAQ/文件等基礎幫助，但不在上下文中 |
| 3 | 文件可搜尋且基本面向任務 |
| 4 | 在正確時刻提供正確的上下文幫助 |

---

#### 得分彙總

滿分 40（10 項 × 4）。36–40 為優秀，僅需精修；28–35 為良好，應補弱項；20–27 為可接受，但使用者滿意前需顯著改進；12–19 為較差，核心體驗需要大修；0–11 為嚴重，目前不可用，需重新設計。

存在 `n/a` 時，最高分低於 40，按百分比而非原始分數套用區間：90%+ 優秀，70%+ 良好，50%+ 可接受，30%+ 較差，更低為嚴重。例如 24/32 = 75%，評級為良好。

---

#### 問題嚴重度（P0–P3）

| 優先順序 | 名稱 | 描述 | 操作 |
|---|---|---|---|
| **P0** | 阻斷 | 完全無法完成任務 | 立即修復，是釋出阻斷項 |
| **P1** | 重大 | 引發顯著困難或困惑 | 釋出前修復 |
| **P2** | 次要 | 令人煩惱但存在繞過方式 | 下一輪修復 |
| **P3** | 精修 | 值得修但無實際使用者影響 | 時間允許時處理 |

不確定等級時，問：“使用者會因此聯絡支援嗎？”若會，至少是 P1。

### 基於 Persona 的設計測試

從五種不同使用者原型觀察介面。每個 Persona 都會暴露單一“設計總監”視角遺漏的失敗模式。按介面選擇最相關的 2–3 個，讓他們走完主要操作，報告具體風險而非泛泛擔憂。

---

#### 1. 急躁的高階使用者：“Alex”

熟悉同類產品，追求效率，討厭手把手指導；會尋找捷徑，否則離開。他會跳過 onboarding、尋找快捷鍵、嘗試批次與自動化，並厭惡低風險操作的冗餘步驟。

檢查：能否在 60 秒內完成核心任務；常用操作有無快捷鍵；onboarding 能否完全跳過；彈窗能否用 Esc 關閉；是否有批次操作等高階路徑。風險包括強制教程、主操作不能鍵盤完成、不可跳過的慢動畫、適合批次卻逐項處理、低風險動作反覆確認。

---

#### 2. 困惑的新使用者：“Jordan”

從未使用此類產品，每一步都需要指導，寧可放棄也不願猜。他會仔細讀說明、對陌生控制元件猶豫、不斷尋找幫助、誤解術語，並按字面理解標籤。

檢查：5 秒內能否看出首個操作；圖示是否有文字；決策點有無上下文幫助；術語是否假設先驗知識；每步有無返回/撤銷。風險包括純圖示導航、未解釋的術語、沒有可見幫助、操作後下一步模糊、成功後沒有確認。

---

#### 3. 依賴無障礙能力的使用者：“Sam”

使用 VoiceOver/NVDA 或僅鍵盤導航，也可能低視力、行動受限或有認知差異。他按順序 Tab，依賴 ARIA 與標題結構，看不到 hover 或純視覺訊號，需要至少 4.5:1 對比度，並可能放大到 200%。

檢查：主要流程能否全鍵盤完成；互動元素是否可聚焦且焦點清晰；圖片有無有意義 alt；文字對比度是否滿足 WCAG AA；載入、成功、錯誤等狀態變化是否被讀屏播報。風險包括只有點選的互動、缺失焦點、僅以顏色傳意、無標籤欄位/按鈕、不可延長的限時操作、破壞讀屏流程的自定義元件。

---

#### 4. 主動壓力測試者：“Riley”

有條理地越過 happy path，測試邊界、意外輸入和體驗缺口。他會嘗試空狀態、超長字串、特殊字元、emoji、RTL 和 Excel 貼上，也會後退、流程中重新整理、多標籤開啟，並核對 UI 承諾與實際結果。

檢查：0 項、1000 項和超長文字時如何；錯誤能否恢復；中途重新整理是否儲存狀態；是否有表面可用卻產出錯誤結果的功能；如何處理意外輸入。風險包括靜默失敗、暴露技術細節或破壞介面的錯誤處理、無指導的空狀態、重新整理/導航丟資料，以及相似操作行為不一。

---

#### 5. 分心的移動使用者：“Casey”

在路上單手使用手機，經常中斷，網路可能較慢。偏好拇指可達的底部操作，在應用間切換，注意力和耐心有限，儘量少輸入、更多點選選擇。

檢查：主操作是否位於螢幕下半部拇指區；離開再返回是否保留狀態；3G 下是否可用；表單是否有自動補全與智慧預設值；觸控目標是否至少 44×44pt。風險包括頂部不可達操作、切換後丟進度、本可選擇卻要求長文字、每頁重複載入重資源，以及觸控目標太小或過密。

---

#### 選擇 Persona

| 介面型別 | 主要 Persona | 原因 |
|---|---|---|
| 著陸頁 / 營銷 | Jordan、Riley、Casey | 第一印象、信任、行動版 |
| Dashboard / 管理後台 | Alex、Sam | 高階效率、無障礙 |
| 電商 / 結賬 | Casey、Riley、Jordan | 行動版、邊界情況、清晰度 |
| Onboarding 流程 | Jordan、Casey | 困惑、中斷 |
| 資料密集 / 分析 | Alex、Sam | 效率、鍵盤導航 |
| 表單密集 / 指南 | Jordan、Sam、Casey | 清晰度、無障礙、行動版 |

#### 專案專用 Persona

若 `{{config_file}}` 包含由 `impeccable init` 產生的 `## Design Context`，從受眾與品牌資訊派生 1–2 個額外 Persona：讀取目標受眾描述；找出五個預設未覆蓋的主要原型；按下列模板建立：

```
##### [Role]: "[Name]"

**Profile**: [2-3 key characteristics derived from Design Context]

**Behaviors**: [3-4 specific behaviors based on the described audience]

**Red Flags**: [3-4 things that would alienate this specific user type]
```

只有存在真實 Design Context 資料時才產生專用 Persona。不得虛構受眾細節；無上下文時使用五個預設 Persona。
