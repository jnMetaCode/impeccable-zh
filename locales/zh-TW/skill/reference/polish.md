Polish 是精修，絕不能暗中變成重新設計。保留現有的視覺世界、內容、行為以及範圍外的一切。如果概念本身有問題，應明確指出，並建議重新設計或使用 `bolder`，不要偷偷替換方案。

偵測器的結果只能證明存在缺陷，不能證明品質達標。必須檢查實際渲染體驗和真實互動路徑。

## 1. 建立系統認知

閱讀 DESIGN.md，並檢視有代表性的 token、共享元件、模式和相鄰流程。如果沒有正式設計系統，就遵循專案中連貫一致的慣例。

修復前先對每一處偏差分類：

- **缺少 token：** 系統需要一個可複用的值；
- **一次性實作：** 應改用現有共享元件或模式；
- **概念不匹配：** 流程、資訊架構或層級與產品中的相似區域不同；
- **區域性缺陷：** 實作本身不完整或不一致。

在最小且正確的層級修復根因。如果無法推斷具有約束力的系統原則，應先詢問。

## 2. 收集證據

親自以介面的代表性尺寸使用該功能：Web 端檢查桌面與行動版；原生平臺（`ios` / `android` / `adaptive`）則按照相應平臺參考文件中“驗證建置”的說明，在模擬器、模擬器或真機上覆蓋已釋出的裝置類別並截圖。確認：

- 路徑在功能上是否完整；
- 預期品質標準和可用時間；
- 已知限制或刻意暫未完成的工作；
- 使用者實際會遇到的狀態、內容長度、角色和輸入方式。

如果已有評審記錄，將它作為一項輸入：

```bash
{{scripts_path}}/impeccable critique-storage latest "<resolved target>" --json
```

退出碼 0 會返回 JSON，其中包含最新快照的 `body` 和精確的 `snapshot_file` 標識。保留 `snapshot_file`，直到本輪結束。對於本地檔案目標，輔助工具會把檔案目前內容的精確指紋與評審時記錄的指紋比較。未變化的已暫存、未暫存或未跟蹤內容仍視為目前版本；任何位元組變化、檔案刪除或被非檔案物件替代，都會關閉它所識別的待辦，同時保留趨勢歷史，並以退出碼 2 結束。URL 目標沒有本地指紋，在顯式關閉前始終視為目前版本。當快照仍為目前版本時，納入 `body` 中相關的 P0/P1 問題，並說明讀取了哪個快照。退出碼 2 表示不存在快照或目標已變化。無論哪種情況，都要獨立完成一輪檢查。

## 3. 分診

將功能缺陷與外觀問題分開，並按以下順序修復：

1. 中斷或阻塞任務、造成資料丟失、狀態誤導和無障礙路徑失效的問題；
2. 缺少載入、空、錯誤、成功、停用和權限狀態；
3. 流程、層級、回應式行為和設計系統偏差；
4. 視覺與動效不一致；
5. 程式碼和資源清理。

不要在其他區域仍低於同一品質標準時，只把一個角落打磨到完美。

## 4. 精修完整路徑

### 流程與層級

- 與相鄰功能的心智模型、術語、漸進披露、路由、儲存行為，以及樂觀或悲觀更新模式保持一致。
- 讓主要任務和目前狀態一目瞭然，同時避免把所有元素壓成同一權重。
- 確保進入、過渡、空狀態和恢復路徑彼此連通，而不是像孤立頁面一樣各自執行。

### 佈局與文字

- 對齊專案的網格和間距尺度；既修正數學對齊，也修正視覺對齊。
- 緊密組合相關內容，並用充足間距分隔不同組。
- 相同角色的排版應保持一致；測試行長、換行、在地化擴張、縮放和字型載入。
- 驗證每個受支援的視口，而不是隻修正目前截圖。

### 色彩、影像與圖示

- 使用語義 token，並讓顏色含義在不同主題中保持穩定。
- 驗證每種狀態下文字、控制元件和焦點的對比度。
- 保持圖示家族、描邊或字重、尺寸和視覺對齊一致。
- 防止圖片引起佈局偏移；使用正確的寬高比、回應式圖片源和有用的 alt 文字。

### 互動與狀態

- 每個控制元件都需要恰當的 default、hover、focus、active、disabled、loading、error 和 success 行為。
- 保留可見的鍵盤焦點、合理的 Tab 順序、標籤，以及符合平臺規範的觸控目標。
- 動效應連貫、可中斷且效能良好。不要僅為了讓精修顯得可見而新增動畫。
- 驗證產品可能遇到的超長、缺失、在地化、離線、慢速和權限受限內容。

### 內容與程式碼

- 保持術語、大小寫、標點和事實性文案一致。修改事實陳述前先詢問。
- 刪除除錯輸出、死程式碼、未使用的 import、過時樣式和精修過程中產生的重複實作。
- 如果某種模式歸設計系統所有，用共享元件替換自定義實作。
- 將真正可複用的值提升為 token；不要為一個區域性例外建立系統抽象。

## 5. 驗證並收尾

再次走完完整路徑，並在適用時使用滑鼠、鍵盤和觸控。檢查：

- Web 端的移動、中間和寬屏佈局；原生端在兩個受支援方向上的手機和平板尺寸類別；
- 載入、空、錯誤、成功、停用、長內容和缺失內容狀態；
- 縮放、對比度、焦點、語義和螢幕閱讀器名稱；
- 所有位置的控制檯錯誤、佈局偏移、互動延遲和圖片載入；Web 端的受支援瀏覽器；原生端的受支援系統版本、執行時警告和掉幀；
- 與 DESIGN.md、相鄰功能及使用者範圍保持一致。

遵循 `impeccable context` 和 hooks 提供的品質指導，然後執行其他相關 QA 命令。只有在沒有自動偵測器執行時，context 才會要求手動掃描；絕不要再增加一輪偵測器掃描。修復真實缺陷，只記錄範圍明確且有意保留的例外。偵測結果乾淨不能替代視覺判斷。

最後檢查原始碼 diff：刪除意外改動、孤立程式碼、冗餘值和臨時產物。只有當功能在完整路徑上已經完備且精修一致時，才能釋出。

當本輪處理的某個快照中的全部 Priority Issue 都已解決時，關閉該快照：

```bash
{{scripts_path}}/impeccable critique-storage close "<resolved target>" "<snapshot_file returned by latest>"
```

這隻會關閉本輪實際處理的快照；如果期間產生了更新的評審，其待辦仍然有效。在沒有讀取快照、沒有保留 `snapshot_file` 或仍有 Priority Issue 時，不要關閉快照。
