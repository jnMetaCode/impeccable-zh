# Extract 流程

識別可複用模式、元件和設計 token，再將它們提取並整合進設計系統，以便系統性複用。

## 步驟 1：發現設計系統

找到設計系統、元件庫或共享 UI 目錄。瞭解其結構：元件組織方式、命名慣例、設計 token 結構和匯入匯出慣例。

**關鍵要求**：如果不存在設計系統，暫時不要建立。{{ask_instruction}} 先了解首選位置和結構。

## 步驟 2：識別模式

在目標區域中尋找適合提取的內容：

- **重複元件**：使用三次以上的相似 UI 模式，例如按鈕、卡片和輸入框
- **硬編碼值**：應成為 token 的顏色、間距、排版和陰影
- **不一致的變體**：同一概念存在多種實作
- **組合模式**：重複出現的佈局或互動模式，例如表單行、工具欄分組和空狀態
- **文字樣式**：重複出現的字號、字重與行高組合
- **動畫模式**：重複出現的緩動、時長或關鍵幀組合

評估價值：只有同一意圖下使用三次以上的內容才應提取。過早抽象比重複更糟。

## 步驟 3：規劃提取

制定系統化計劃：

- **要提取的元件**：哪些介面元素應成為可複用元件？
- **要建立的 token**：哪些硬編碼值應成為設計 token？
- **需要支援的變體**：每個元件需要哪些變化形式？
- **命名慣例**：符合現有模式的元件名、token 名和 prop 名
- **遷移路徑**：如何重構現有用法，使其改用新的共享版本

**重要要求**：設計系統應逐步成長。只提取現在已經明確可複用的內容，而不是所有未來可能複用的內容。

## 步驟 4：提取並增強

建置經過改進的可複用版本：

- **元件**：清晰的 props API、合理預設值、適用於不同場景的正確變體、內建無障礙能力（ARIA、鍵盤導航、焦點管理），以及文件和使用示例
- **設計 token**：清晰命名（基礎 token 與語義 token）、正確層級和組織方式，以及每個 token 的使用說明
- **模式**：何時使用該模式、程式碼示例、變體與組合方式

## 步驟 5：遷移

用新的共享版本替換現有用法：

- **找到全部例項**：搜尋已提取模式的所有用法
- **系統性替換**：更新每處用法，使其使用共享版本
- **充分測試**：確保視覺和功能一致
- **刪除死程式碼**：移除舊實作

## 步驟 6：編寫文件

更新設計系統文件：

- 將新元件加入元件庫
- 記錄 token 的用途和值
- 新增示例和使用指南
- 更新 Storybook 或元件目錄

**絕對不要**：
- 未經泛化就提取一次性、特定情境的實作
- 建立泛化到失去用途的元件
- 不考慮現有設計系統慣例就提取
- 省略正確的 TypeScript 型別或 prop 文件
- 為每一個值都建立 token，token 必須具有語義
- 提取意圖不同的內容，兩個外觀相似但用途不同的按鈕應繼續分開
