執行系統化的**技術**品質檢查並產生完整報告。不要修復問題；記錄問題，交給其他命令處理。

這是程式碼級稽核，不是設計評審。檢查實作中可以測量和驗證的內容。

**僅適用於 Web。** 原生平臺（`ios` / `android` / `adaptive`）應改用 [audit.native.md](audit.native.md)；如果專案是原生應用，立即切換。

## 診斷掃描

全面檢查 5 個維度，並按以下標準分別評分 0～4。

### 1. 無障礙（A11y）

**檢查**：
- **對比度問題**：文字對比度低於 4.5:1（AAA 為 7:1）
- **動態效果敏感性**：`prefers-reduced-motion` 需要有意設計的替代方案，同時保留狀態變化和層級；標記會破壞有用回饋的全域性 `0.01ms` 動畫清除、超過閾值的閃爍，以及阻礙焦點、閱讀或任務完成的動效
- **缺少 ARIA**：互動元素沒有正確的 role、label 或 state
- **鍵盤導航**：缺少焦點指示器、Tab 順序不合理或存在鍵盤陷阱
- **語義化 HTML**：標題層級錯誤、缺少 landmark、使用 div 代替 button
- **Alt 文字**：圖片說明缺失或品質差
- **表單問題**：輸入框沒有標籤、錯誤提示不清楚、缺少必填標記

**評分 0～4**：0=不可訪問（未透過 WCAG A）；1=重大缺口；2=部分支援但仍有顯著缺口；3=良好，基本達到 WCAG AA；4=優秀，完整達到 WCAG AA 並接近 AAA

### 2. 效能

**檢查**：
- **佈局抖動**：在迴圈中交替讀取和寫入佈局屬性
- **昂貴動畫**：隨意動畫化佈局屬性、無邊界的 blur/filter/shadow，或明顯掉幀的效果
- **缺少最佳化**：圖片未延遲載入、資源未最佳化
- **濫用 will-change**：大範圍應用或靜止時仍保留 `will-change`；它只應用於已知的昂貴動畫，不是基礎要求
- **Bundle 大小**：不必要的 import、未使用依賴
- **渲染效能**：不必要的重新渲染、缺少 memoization

**評分 0～4**：0=問題嚴重；1=重大問題；2=部分最佳化但仍有缺口；3=良好，可小幅改進；4=優秀，快速、精簡且最佳化充分

### 3. 主題

**檢查**：
- **硬編碼顏色**：顏色沒有使用設計 token
- **深色模式損壞**：缺少深色變體或深色主題對比度差
- **Token 不一致**：使用錯誤 token 或混用 token 型別
- **主題切換問題**：切換主題時某些值不更新

**評分 0～4**：0=沒有主題系統；1=幾乎全部硬編碼；2=有 token 但使用不一致；3=良好，僅少量硬編碼；4=優秀，token 系統完整且深色模式完全正常

### 4. 回應式設計

**檢查**：
- **固定寬度**：硬編碼寬度導致行動版損壞
- **觸控目標**：互動元素小於 44×44px
- **觸控互動損壞**：自定義 slider、拖動區域和可滾動控制元件條的主要手勢在觸控下失效、吞掉頁面滾動、拖動被頁面滾動奪走，或手勢中斷後保持卡住。程式碼跡象包括只處理滑鼠、pointer 拖動區域沒有 `touch-action`、cancel、失去 capture 或 blur 時沒有清理拖動狀態。瀏覽器工具能模擬觸控時應實際執行手勢；渲染視口只能證明佈局，不能證明手勢。說明證據來自模擬視口、合成觸控、哪個引擎或真機，並指出哪些內容尚未測試
- **水平滾動**：窄視口出現內容溢位
- **文字縮放**：增大字號後佈局損壞
- **缺少斷點**：沒有行動版或平板變體

**評分 0～4**：0=僅桌面可用；1=重大問題；2=行動版可用但粗糙；3=良好，僅少量觸控目標或溢位問題；4=優秀，所有視口流暢，觸控目標正確且手勢真實可用

### 5. 實作完整性（關鍵）

執行隨附偵測器，並結合上下文驗證每項發現。尋找重複的實作捷徑、設計系統漂移、誤導或純裝飾內容，以及可與無關產品互換的結構。把確定性發現與視覺判斷分開，並明確指出誤報。

**評分 0～4**：0=系統性漂移；1=重複出現重大失敗；2=存在若干經驗證的問題；3=僅有孤立的小問題；4=連貫且有明確意圖

### 按嚴重度列出詳細發現

每個問題標記 **P0～P3 嚴重度**：
- **P0 阻塞**：阻止任務完成，立即修復
- **P1 重大**：造成顯著困難或違反 WCAG AA，釋出前修復
- **P2 次要**：令人困擾但有替代方案，下一輪修復
- **P3 精修**：可修可不修，對使用者沒有實質影響，有時間再處理

每個問題記錄：
- **[P?] 問題名稱**
- **位置**：元件、檔案、行號
- **類別**：無障礙 / 效能 / 主題 / 回應式 / 實作完整性
- **影響**：如何影響使用者
- **WCAG/標準**：違反的標準（如適用）
- **建議**：如何修復
- **建議命令**：使用哪個命令（優先：{{available_commands}}）

### 模式與系統性問題

識別代表系統缺口而非一次性錯誤的重複問題，例如：
- “15 個以上元件出現硬編碼顏色，應使用設計 token”
- “整個行動版體驗中的觸控目標普遍小於 44px”

### 正面發現

記錄做得好的實踐，以便保持和複用。

## 建議操作

按優先順序列出建議命令（先 P0，再 P1，然後 P2）：

1. **[P?] `{{command_prefix}}command-name`**：簡要說明（引用稽核發現的具體上下文）
2. **[P?] `{{command_prefix}}command-name`**：簡要說明（具體上下文）

**規則**：只能推薦以下命令：{{available_commands}}。把發現對映到最合適的命令。如果推薦了任何修復，最後一步必須是 `{{command_prefix}}impeccable polish`。

展示摘要後，告訴使用者：

> 你可以讓我逐項執行、一次全部執行，或按你希望的任意順序執行。
>
> 修復後重新執行 `{{command_prefix}}impeccable audit`，檢視分數是否提高。

**重要要求**：全面但可執行。過多 P3 會製造噪音，應聚焦真正重要的問題。

**絕對不要**：
- 報告問題卻不解釋影響
- 提供泛泛建議，必須具體且可執行
- 跳過正面發現
- 忘記排優先順序，不可能所有問題都是 P0
- 未經驗證就報告誤報
