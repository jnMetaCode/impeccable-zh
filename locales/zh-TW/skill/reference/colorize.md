用色彩建立層級、含義和氛圍。保留已經確認的品牌和語義慣例；不要以增加色彩為名替換整個視覺世界。

## 訪客模式

- **Persuade + Experience：** 當所選視覺世界需要時，色彩可以承載語氣並佔據大面積區域。
- **Operate + Read：** 色彩主要編碼操作、選擇、狀態、導向和閱讀層級。強調色越少見，力量越強。

## 選擇前先稽核

閱讀 DESIGN.md、token、資源、目前主題和代表性狀態。識別：

- 哪些顏色是已經確認的品牌承諾；
- 目前表面、文字、操作和語義角色；
- 灰度導致層級或狀態不清的位置；
- 對比度失敗和僅靠顏色傳達的資訊；
- 淺色或深色模式以及資料視覺化要求；
- 任務需要更多顏色，還是需要新的視覺身份。

如果需要新視覺身份，使用 [new-work.md](new-work.md)。只有無法推斷具有約束力的品牌決策時才詢問。

## 選擇策略

編輯前明確預期情緒溫度、主導關係、對比範圍和用色劑量。策略可以剋制，也可以沉浸，但必須服從簡報和所選視覺世界，而不是固定百分比規則。

建立角色，而不是堆積色板：

- 畫布和抬升表面；
- 主要與次要文字；
- 操作、焦點和選擇；
- 邊框和分隔線；
- 成功、警告、錯誤和資訊；
- 必要時的資料類別或尺度。

使用專案現有色彩空間。新的 Web 色板優先使用 OKLCH，因為它能可預測地調整明度和色度。根據產品含義和視覺方向選擇色相，絕不要依賴品類預設聯想。

## 在系統尺度上應用

- 讓最強的顏色佔據一個明確區域或角色，而不是散落微小強調色。
- 讓主要操作容易被找到；不要把它的顏色浪費在裝飾上。
- 只有品牌色相確實能增強凝聚力時才給中性色染色。只要符合視覺世界，中性灰完全有效。
- 在彩色表面上，根據前景色或表面色相推導次要文字，不要使用褪色的通用灰。
- 保持語義含義一致，但應尊重平臺和領域慣例，不要假設固定色相。
- 資料不能只靠顏色編碼，還應使用不同的明度、色度、形狀、標籤或圖案。
- 深色模式應顯式設計表面層級和對比度，不要機械反轉淺色主題。
- 專案存在 token 系統時，定義基礎值和語義 token。主題變化通常應重新對映語義角色。

與層級、狀態、內容或視覺世界沒有關係的裝飾不構成色彩策略。

## 對比度與感知

驗證計算後的前景色與背景色組合：

| 內容 | WCAG AA 最低要求 |
|---|---|
| 正文 | 4.5:1 |
| 大號文字 | 3:1 |
| 控制元件、圖示、焦點指示器 | 3:1 |

不要只依賴肉眼判斷。檢查互動狀態、浮層、圖片上的文字、停用內容和兩種主題。模擬常見色覺缺陷。用顏色傳達的資訊還需要文字、形狀、圖示或位置作為輔助。

推導 OKLCH 色階時，應改變明度，並在接近白色和黑色時降低色度。不要為了數學上的整齊，在極端明度下維持高色度。當透明度會使對比度依賴上下文時，優先使用明確顏色，而不是層層疊加半透明色。

## 驗證

- 每種顏色都有穩定角色或視覺世界特有的氛圍用途。
- 注意力落在預期操作、內容或狀態上。
- 色板適用於安靜、密集、互動、錯誤和空狀態。
- 淺色和深色主題都經過獨立構圖，而非機械反轉。
- 所有相關狀態的對比度和非顏色提示均達標。
- 結果能明確屬於該產品，而不是通用的“多彩”處理。

色板的存在有充分理由後，交給 `{{command_prefix}}impeccable polish` 完成最終精修。

## Live 模式簽名參數

從 Live 模式呼叫時，每個變體都宣告一個 `color-amount` 參數。基於 `var(--p-color-amount, 0.5)` 編寫 CSS，使使用者無需重新產生，就能從中性狀態調到該變體完整的色彩策略。

```json
{"id":"color-amount","kind":"range","min":0,"max":1,"step":0.05,"default":0.5,"label":"Color amount"}
```

最多新增兩個變體專屬參數，例如色板、溫度或染色行為。遵循 [live.md](live.md) 的參數契約。
